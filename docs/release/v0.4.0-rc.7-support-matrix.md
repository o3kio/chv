## Maturity tiers

The labels are the vocabulary defined in
[`docs/DEPLOYMENT-ARCHITECTURE.md`](../DEPLOYMENT-ARCHITECTURE.md) §1.2:
**[QUALIFIED — KVM-VERIFIED]**, **[CI-VERIFIED]**,
**[CONTAINER-VERIFIED]**, **[CODE-SUPPORTED, UNQUALIFIED]**,
**[DESIGN-ONLY]**, and **[UNSUPPORTED/ABSENT]**. The qualification host is a
single shared nested-KVM host; nothing here is multi-host- or field-qualified.

## What is explicitly not claimed

- **Real-KVM behavior of the rc.7 runtime.** The full lane covers the
  pre-rc.6 runtime (`c1effc71`); rc.6 and rc.7 change the agent boot verdict,
  the agent unit, the nwd dnsmasq spawn paths, the installer's default-network
  seed, and the `--wipe` authority removal, which that lane does not exercise.
- **A green rc.7 post-publication lane.** None has run at tag time. The rc.6
  lane did not run either, and rc.6 is disqualified by its clean-install
  blocker report.
- **Field qualification.** The field window starts from rc.7 after
  publication and the required clean-install drills; no field evidence exists
  yet.
- **A clean-install DHCP lease on rc.7.** B1/B3/B4 are covered by unit and
  packaging tests and by the rc.6 pre-window mechanism probes; the published
  rc.7 artifact has not yet served a lease on the field host.
- **Guest-OS shutdown on removal.** Removal is a VMM-level `SIGTERM`/`SIGKILL`
  after 10 s; stop guests through the API if their buffers must flush.
- **A fix for M2.5 delete retention.** It remains a disclosed pre-existing residual:
  the BFF/CP rows, VM directory, volume row, and backing file persist after a
  successful delete; the task/operation result is the truthful signal.
- Multi-host control-plane/agent operation, multi-host migration, and the
  stretched-L2 fabric.
- Concurrent-write ("live") migration without the pause-first gate.
- Ceph RBD / iSCSI storage; K8s/CNI, Docker-forwarded, or multi-bridge
  coexistence.
- Backup/restore as disaster recovery.
- Any concurrency, density, throughput, or requests-per-second figure.
- Rolling node upgrade or downgrade. A fresh-host install + package upgrade +
  uninstall demonstration exists for `v0.4.0-rc.1` as a **container** contract
  (run [42042149140](https://github.com/o3kio/chv/actions/runs/42042149140)).
  `v0.4.0-rc.2` is disclosed as defective for clean installs and is not used
  as install evidence. `v0.4.0-rc.3`'s tarball/package path is fixed, but its
  quick installer is defective. `v0.4.0-rc.4`'s tarball/package path passed
  its lane, but its quick installer is defective, fixed in rc.5. `v0.4.0-rc.5`
  passed its container lane but failed the field restart drill and is
  superseded by rc.6. `v0.4.0-rc.6` fixed the restart drill but is disqualified
  by the clean-install blocker report, superseded by rc.7. The rc.5 lane
  ([42159563210](https://github.com/o3kio/chv/actions/runs/42159563210))
  remains the evidence for the #727 installer fixes only. None of this is
  bare-metal or cloud-VM evidence.
- Volvisor-backed storage orchestration.
- Bare-metal KVM behavior (all qualification ran nested) and host-reboot
  recovery (the cold-restart leg is the labeled subset).

## Residual boundaries that survive this matrix

These are disclosed, not hidden: the new-install data-loss defect in
`v0.4.0-rc.1`/`v0.4.0-rc.2`/`v0.3.0` (fixed in `scripts/install.sh` for rc.3,
#722) and in the `v0.4.0-rc.3` **quick installer** (fixed in rc.4, #725); the
`v0.4.0-rc.4` quick-installer enrollment and re-run defects (fixed in rc.5,
#727; see the [rc.5 release notes](v0.4.0-rc.5-release-notes.md) §2); the
**`v0.4.0-rc.5` agent-restart defect** (VMM killed, `TimeoutStopSec` stop, and
`RuntimeDirectory=chv` unlinking the stord/nwd sockets; fixed in rc.6, #732;
see the [rc.6 release notes](v0.4.0-rc.6-release-notes.md) §2); the
**`v0.4.0-rc.6` clean-install blockers** (device cgroup denied
`/dev/net/tun`, swallowed `vm.boot` failure, duplicate default gateway,
unwritable dnsmasq lease file, and the `--wipe` identity conflict; fixed in
rc.7, see the [rc.6 blocker report](../evidence/production-readiness/v0.4.0/field-qualification/01-rc6-blockers.md)
and [rc.7 release notes](v0.4.0-rc.7-release-notes.md) §2); the
VMM/serial containment boundary (#345/#409 at v53.0); M2.5 delete retention
(BFF/CP rows, VM directory, volume row, and backing file persist after a
successful delete; the task/operation result is the truthful signal); the
late serial write after `SHUT_RD` (bounded and `vm.reboot`-recoverable);
VMM adoption only under `/var/lib/chv/agent/vms` (custom `CHV_DATA_DIR` not
covered); `INSTALL_CHV_BRIDGE_NAME` overrides covered by the baseline
fallback but a custom baseline CIDR outside the installer/database sources
not; `preremove.sh` without systemd can leave already-running stord/nwd
processes (the package path uses systemd); a PID-reuse window between
identifying and signalling a VMM; netns-only discovery limited to `default`
plus legacy hex ids; `install.sh`'s wipe path still carrying the pre-existing
`/24` hardcode for the baseline CIDR; JWT/encryption-key coupling (#336); the
#582 multi-volume convergence-skew residual; the #706 audit crash window (a
mutation can commit before its audit row is written; mTLS interceptor denials
write no audit row); and the requirement to set distinct `metrics_bind` values
when running more than one stord per host. A fresh rc.7 install (or a `--wipe`
rebuild) fixes the device policy, boot verdict, DHCP lease, default-gateway,
and `--wipe` identity paths. A **package-only** upgrade
preserves host network configuration, so the legacy `chvbr0` from rc.6 must
be removed once (documented in the [rc.7 release notes](v0.4.0-rc.7-release-notes.md)
§4) before guest connectivity is judged. Neither upgrade form restores writes
or VMs already lost, and a VM that lost its NIC under rc.6 must be deleted and
recreated. The detached-open
session (#711) and first-enrollment bootstrap audit gap
(#709) were residuals of the real-KVM-qualified candidate `e82d49a1`. Both
fixes are in the rc.2 build; the rc.2 lane exercises #711 (F7 deletes a base
VM created before an agent restart and asserts zero live stord sessions) and
asserts #709 (the deploy leg reads `node_bootstrap_results.success = 1` on
the issued identity). The residual wording below is retained only for
pre-upgrade stord data, which the fix cannot retroactively rewrite. Sessions
orphaned by a crash on a pre-upgrade stord (old detach left
`runtime_status = "open"`) are not reclaimed by the VM-delete sweep, because
they cannot be distinguished from a live opened-but-attach-pending session;
`DeleteVolume` closes every session with no attached VM before destroying, so
these orphans clear on volume destroy. A session still attached to a VM keeps
the destroy refusal; if a failed drain left a dead VM's id on the row, detach
that volume from the named VM before attempting the delete — a failed delete
attempt tombstones the volume `'Deleting'`, which refuses the detach and
replays the failure on retry. The detach mutation honors an explicit `vm_id`,
so it can name the dead VM after the control plane cleared the attachment. The
full list is in
[`DEPLOYMENT-ARCHITECTURE.md` §9](../DEPLOYMENT-ARCHITECTURE.md#9-known-boundaries-and-residual-risk).
