## 1. This is a release candidate, not stable

This build is for evaluation and staged rollout with an operator who has read
the support matrix and the known limitations. It does **not** claim multi-host
operation, HA/control-plane failover, live (concurrent-write) migration,
backup/restore as DR, Ceph/iSCSI storage, Volvisor-backed storage, RPM
behavior on a real host, arm64, or any scale figure.

No field-qualification campaign has run. The rc.6 blocker investigation was a
**pre-window** clean-install drill, not a field day. The campaign
([plan](../plans/2026-11-05-v0.4.0-field-qualification.md), profile in
[`DEPLOYMENT-ARCHITECTURE.md`](../DEPLOYMENT-ARCHITECTURE.md) §5 UC-11) starts
from a clean rc.7 install and runs for 21–30 days. A passing field campaign
is an input to the stable decision, not a pre-approval.

## 2. Why rc.7 exists: published rc.6 failed a clean install

`v0.4.0-rc.6` was cut to fix the rc.5 agent-restart defect. Its own clean
install, run from the **published** rc.6 tarball on `field-host-1` (run 3,
`rc=0` in 22 s), then reproduced the defects below. The rc.6 container lane
and the pre-publication unit/removal drills did not exercise these paths.

| # | Finding | Class at rc.6 |
|---|---|---|
| **B1** | The agent unit's device cgroup denies `/dev/net/tun`. Cloud Hypervisor cannot attach a virtio-net device, so every boot fails with `Couldn't open /dev/net/tun: Operation not permitted`; the VM has no NIC. | **blocker** |
| **B2** | `start_vm` reports success when `vm.boot` returns HTTP 500: the VMM stays `Created`, the BFF displays the desired `Running` state, and the operation is recorded `succeeded`. | **blocker** |
| **B3** | A default install creates the legacy `chvbr0` and the nwd default-network bridge with the same `10.200.0.1/24` address. The host routes guest traffic to the dead `chvbr0`; guest ARP fails. | **operational defect (plan §6.2)**; blocks the profile as configured |
| **B4** | dnsmasq has no writable lease file. Its compiled default (`/var/lib/misc/dnsmasq.leases`) is outside nwd's `ProtectSystem=strict` writable roots, so it exits `Permission denied` and DHCP never serves a lease. | **blocker** for the documented network profile |
| **B5** | `install.sh --wipe` retains `core.db`, the runtime-authority lease, and the node-cache archive while regenerating the node identity in `agent.toml`. The new agent crash-loops on `Identity(Conflict)`. | **blocker** (failed documented removal/recovery) |
| **B6** | After a failed first boot, a retried start can report `Running` with `config.net=[]` and a 0-byte console. Stop/start does not heal it; delete + recreate is the only recovery. | **consequence of B1/B2**; recovery contract |
| **B7** | Local release-directory/tarball mode prints `Version: 0.3.0` in the completion banner and records it in the install log while installing the actual rc artifact (the offline fallback pin, not the release artifact's version). | **operational truth defect** (not blocker-class; found in the rc.6 clean-install evidence); fixed in rc.7 because that transcript is the field artifact record |

Key reproduction facts (raw evidence in
[`artifacts/03-rc6-blockers/`](../evidence/production-readiness/v0.4.0/field-qualification/artifacts/03-rc6-blockers/)):

- **B1:** a raw `vm.boot` against a BFF-created VM returned
  `boot_http=500`, body
  `["…Cannot create virtio-net device","…Couldn't open /dev/net/tun","Operation not permitted (os error 1)"]`,
  VMM `state_after=Created`, console 0 bytes. With a runtime device-cgroup
  allowance for `/dev/net/tun`, the unchanged nwd tap produced
  `start_http=200`, `carrier=1`, five tun file descriptors, a 75,616-byte
  console, and cloud-init `finished` at 7.2 s. Tap ownership was **not** the
  defect: CH runs as `chv` with `CapEff=0` and attaches an ownerless nwd tap.
  No `CAP_NET_ADMIN` is required.
- **B2:** six `start_vm` operations were recorded `succeeded`; four of the
  same operations logged `vm.boot … status=500`. The BFF `power_state` is the
  desired state, not VMM ground truth.
- **B3:** `ip route` showed two `10.200.0.0/24` owners; `ip route get
  10.200.0.175` resolved to `dev chvbr0`; the guest's ARP for its gateway
  stayed `FAILED`.
- **B4:** every nwd start logged
  `cannot open or create lease file /var/lib/misc/dnsmasq.leases: Permission denied`;
  the generated configuration had no lease-file line.
- **B5:** `core.db` held node
  `be476a16-135c-410c-a439-51a3f3c15730` while the regenerated `agent.toml`
  held `d0d70212-03e1-4688-9ebf-45c30d642a8f`; the agent repeated
  `Identity(Conflict { authoritative_source: "existing Core", conflicting_source: "importable NodeCache" })`.

### 2.1 Fixes

- **B1 — packaged device policy.** `packaging/systemd/chv-agent.service` and
  its `docs/examples/systemd` copy now list
  `DeviceAllow=/dev/net/tun rw` alongside `/dev/kvm rw`. Any `DeviceAllow`
  entry switches the unit to a closed device cgroup, so every device Cloud
  Hypervisor opens as a child must be allow-listed. The packaging tests and
  the package smoke check assert both entries.
- **B2 — the operation follows the VMM.** A non-2xx `vm.boot` is now a hard
  failure unless a follow-up `vm.info` reports `Running` or `Paused`
  (auto-boot and a racing retry remain valid). The operation error carries
  the VMM body and observed state instead of a bare `status=500`. The same
  verdict is applied on the re-spawn path.
- **B6 — the NIC assertion is part of the start contract.** After boot, and
  on the idempotent already-running path, the agent compares the NIC count in
  `vm.info`'s `config.net` with the `net` array persisted in
  `vm-config.json`. A VM created with NICs that comes up with fewer fails the
  operation with an explicit `Delete and recreate the VM to recover.` No
  assertion is imposed on a VM created without NICs or on legacy state with
  no readable payload.
- **B3 — one owner of the seeded gateway.** When the default network is
  seeded through the API, `setup_network` now keeps forwarding and NAT but
  removes any legacy `chvbr0` bridge, its persisted networkd/ifupdown config,
  and its NAT rules, then skips creating it and assigning its IP; chv-nwd
  owns the gateway on its own bridge. After seeding, the installer asserts
  that exactly one interface owns the gateway and fails the install
  otherwise. `INSTALL_CHV_NO_SEED=1` retains the legacy bridge path. A
  **package-only** upgrade does not run host-network migration (see §4).
- **B4 — explicit lease file on every spawn path.**
  `executor.rs`, `dhcp.rs`, and `dns.rs` pass
  `--dhcp-leasefile=/run/chv/nwd/dnsmasq-<network_id>.leases`; stop/cleanup
  removes it with the other dnsmasq runtime files. `/run/chv/nwd` is already
  in nwd's `ReadWritePaths`.
- **B5 — `--wipe` removes identity-bound authority state.** After every Core
  writer is stopped and before the node identity is regenerated, `--wipe`
  removes `core.db` plus its WAL/SHM/journal, the
  `.core.db.cellhv-runtime-authority.lease`, the `node-cache-v1.archive`,
  and its authority lock. That authority-state step is scoped to those seven
  paths and never runs on a normal stop/restart. `--wipe` is otherwise a full
  teardown: it also removes `/etc/chv` (including its certificates) and the
  legacy agent certificate copies, so back those up first if they must be
  retained. Two
  consecutive `--wipe` installs must reach `TenantReady`; this is a required
  post-publication drill, not yet claimed at tag time.
- **B7 — the install record names the artifact it installed.** In local
  release-directory and tarball mode, `resolve_version` now derives the
  version from the `chv-<version>-linux-amd64` name instead of reporting the
  offline fallback pin. The rc.6 run-3 transcript printed `Version: 0.3.0`
  while installing `0.4.0-rc.6`; that line is preserved as evidence and
  annotated here. An explicitly pinned `INSTALL_CHV_VERSION` still wins, and
  `fallback_version` remains `0.3.0` for the genuine offline path.

## 3. What changed since v0.4.0-rc.6

### Product

- `packaging/systemd/chv-agent.service` and
  `docs/examples/systemd/chv-agent.service`: `/dev/net/tun` device
  allowance (B1).
- `crates/chv-agent-runtime-ch/src/process.rs`: boot-outcome verification,
  requested-NIC assertion, VMM-body propagation, and the mock coverage for
  `500`+`Created`, `500`+`Running`, `204`+empty `config.net`, and the
  idempotent running-no-NIC path (B2/B6).
- `crates/chv-nwd-core/src/{executor,dhcp,dns}.rs`: explicit lease file on
  every dnsmasq spawn path, lease cleanup, and argv tests (B4).
- `scripts/install.sh`: shared forwarding/NAT helper, seeded-network legacy
  bridge/config/NAT removal, single-gateway-owner assertion, `--wipe`
  authority-state removal, dnsmasq lease cleanup, and local release-directory
  version reporting (B3/B5/B7). `scripts/dev-install.sh` also removes the
  lease files.
- Tests: `tests/test_cellhv_core_packaging.py` covers the unit contract, the
  `--wipe` authority helper, the single-gateway rule, and the lease cleanup;
  `scripts/package/smoke-common.sh` asserts both device allowances.

### Documentation

- This note and the rc.7 support matrix supersede rc.6.
- The rc.6 release notes and support matrix carry a disqualified/superseded
  banner; their tag and assets are unchanged.
- `docs/DEPLOYMENT-ARCHITECTURE.md`, `docs/DEPLOYMENT.md`, `README.md`, the
  field plan, and `docs/install/uninstall.md` are re-pinned to rc.7 and
  document the delete/recreate recovery for a VM that lost its NIC.

### Not changed

No control-plane lifecycle, migration, storage, authentication, network
policy, or UI product code changed. The rc.7 product delta is the device
policy, the agent boot verdict and NIC assertion, the nwd lease file, and the
three installer paths above.

## 4. If you already run rc.6 or earlier

- **`v0.4.0-rc.6`:** do not use it as the stable base. A clean rc.6 install
  cannot boot a VM with a NIC under the shipped unit, can report a failed
  boot as success, routes guest traffic to the wrong bridge, cannot serve
  DHCP, and cannot complete a second `--wipe` install. Upgrade to rc.7 and
  repeat the clean-install drill before running the field workload.
- **VMs created on rc.6 that have no NIC:** delete and recreate them after
  upgrading. A retried start and a stop/start cycle do not heal the missing
  `config.net` (B6); rc.7 now fails such a start visibly. Do not reuse a
  volume whose guest never wrote successfully.
- **rc.6 legacy `chvbr0` on an in-place upgrade:** a package-only upgrade
  replaces binaries and units but does not edit host network configuration,
  so the old `chvbr0` and its persisted networkd/ifupdown stanza survive and
  keep the duplicate `10.200.0.1/24` route. Remove it once after the upgrade:
  ```bash
  sudo ip link del chvbr0 2>/dev/null || true
  sudo rm -f /etc/network/interfaces.d/chvbr0 \
             /etc/systemd/network/10-chvbr0.netdev \
             /etc/systemd/network/11-chvbr0.network
  # and any /etc/systemd/network/12-*.network containing "Bridge=chvbr0"
  sudo systemctl restart systemd-networkd 2>/dev/null || true
  ```
  A plain installer re-run refuses while persistent data exists, so do not
  rely on it for this migration; either perform the removal above, or rebuild
  with `install.sh --wipe` (destructive) and let rc.7 create a single owner.
  Re-check that `ip -o -4 addr show` reports exactly one owner of
  `10.200.0.1` before the clean-install drill.
- **`install.sh --wipe` is destructive by design.** From rc.7 it removes the
  node's identity-bound Core authority state as well as the control-plane
  database, VM runtime state, images, UI tree, and host network state. Take a
  backup first if the deployment must be recoverable. A plain re-run without
  `--wipe` still refuses to proceed when persistent data is present.
- **The rc.6 install transcript says `Version: 0.3.0`.** That is B7: local
  release-directory mode printed the offline fallback pin. The installed
  binaries were the published rc.6 build (commit `df86e53`); rc.7 fixes the
  banner. Verify an artifact by its digest and binary commit banner, not by
  the rc.6 banner line.
- **`v0.4.0-rc.5`:** superseded; its restart drill killed the VMM and could
  wedge the node. Do not use it.
- **`v0.4.0-rc.4` and earlier quick installs:** the quick installer could
  complete with no enrolled node (rc.4) or destroy the enrolled identity on a
  re-run (rc.1–rc.4). Do not use those quick installers for a new install or
  an upgrade. rc.5, rc.6, and rc.7 retain the #727 fixes.
- **`v0.4.0-rc.2` and earlier tarball/package installs:** the install path
  could lose API writes from the install-process lifetime. Verify accounts
  and configuration after upgrading.
- Upgrading fixes the product paths. It cannot restore writes or VMs that
  were already lost, and it does not rewrite host network configuration:
  remove the legacy `chvbr0` once as described above before judging guest
  connectivity.

## 5. Known limitations

The authoritative list is the
[support matrix](v0.4.0-rc.7-support-matrix.md) and
[`DEPLOYMENT-ARCHITECTURE.md` §9](../DEPLOYMENT-ARCHITECTURE.md#9-known-boundaries-and-residual-risk).

- **Single host only.** Multi-host control-plane/agent dispatch is
  architecturally absent; ADR-029 is accepted but not implemented. The
  VXLAN/WireGuard fabric is design-only.
- **rc.7 evidence boundary.** At tag time the B1–B5 and B7 fixes are covered
  by targeted Rust tests, packaging contract tests, clippy, and the rc.6
  pre-window field-host mechanism probes. The published rc.7 artifact has
  **no post-publication lane and no field day**; the clean install, upgrade,
  DHCP lease, policy change, nwd restart, and two consecutive `--wipe`
  installs must be repeated after publication before the window opens.
  Nothing in this note claims that run.
- **VMM/serial containment.** Cloud Hypervisor is pinned to v53.0. The silent
  serial-manager thread death and the adopted-VM stop wedge are contained,
  not cured; re-verify at every VMM upgrade (#345 root / #409).
- **Migration is stop-the-world only.** Pause-first is required; live
  concurrent-write migration is not claimed. One multi-volume
  convergence-skew residual is disclosed (#582).
- **Backup/restore is hard-fenced.** All backup/restore routes return
  `501 NOT_IMPLEMENTED`; there is no DR claim or restore validation.
- **Storage.** Local file and LVM are qualified; Ceph RBD and iSCSI are coded
  but unqualified. K8s/CNI, Docker-forwarded, and multi-bridge coexistence are
  not claimed.
- **Upgrade.** Package upgrade is CI-verified; rolling node upgrade is absent
  and downgrade is unsupported. The rc.5 container lane
  ([42159563210](https://github.com/o3kio/chv/actions/runs/42159563210))
  remains the evidence for the #727 installer fixes only. No rc.7
  post-publication lane has run at tag time.
- **Scale.** No concurrency, density, throughput, or requests-per-second
  claim. M4.8 numbers are single-host baselines.
- **Hardware minimums.** "4 cores / 8 GB RAM / 50 GB disk" is an unevidenced
  recommendation, not a qualification-backed envelope.

## 6. Upgrade and verification notes

The release artifact is the published tarball's `scripts/install.sh`
(release-directory mode) and the published `.deb` set. Package versions carry
`~rc.7`; the node row reports the base `0.4.0`, so the artifact is
discriminated by the package version and the binaries' commit banner.

Before the field window opens, the campaign must repeat, on `field-host-1`:

1. `v0.3.0 → rc.7` (or `rc.6 → rc.7`) package upgrade with one control-plane
   restart of the old release before identifiable-state writes; verify
   configuration, database, certificates, operator account, and a running
   VM survive.
2. Uninstall/purge, then a clean rc.7 tarball install.
3. A documented start with the seeded network: `start_http=200`, the VMM
   reports `Running`, `config.net` carries the requested NIC, the guest
   obtains a DHCP lease from `/run/chv/nwd/dnsmasq-<id>.leases`, and the
   console reaches `login:`.
4. A policy change and an nwd restart; the guest keeps its lease and
   connectivity.
5. Two consecutive `--wipe` installs; both reach `TenantReady`.

Only then does the 21–30 day field window start. These are planned steps, not
results; this note does not claim them.
