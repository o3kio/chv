## 1. This is a release candidate, not stable

This build is for evaluation and staged rollout with an operator who has read
the support matrix and the known limitations. It does **not** claim multi-host
operation, HA/control-plane failover, live (concurrent-write) migration,
backup/restore as DR, Ceph/iSCSI storage, Volvisor-backed storage, RPM
behavior on a real host, arm64, or any scale figure.

No field-qualification campaign has run. The rc.7 upgrade/restart drill was a
**pre-window** drill, not a field day. The campaign
([plan](../plans/2026-11-05-v0.4.0-field-qualification.md), profile in
[`DEPLOYMENT-ARCHITECTURE.md`](../DEPLOYMENT-ARCHITECTURE.md) §5 UC-11) starts
from a clean rc.8 install and runs for 21–30 days. A passing field campaign
is an input to the stable decision, not a pre-approval.

## 2. Why rc.8 exists: published rc.7 failed its own recovery contract

The rc.7 release was published and the pre-window upgrade drill was run on
`field-host-1` (package upgrade, services restarted, running VM adopted). The
upgrade itself preserved configuration, database rows, certificates, the node
identity, and the running VM. The drill then reproduced two defects in the
rc.7 product code.

| # | Finding | Class at rc.7 |
|---|---|---|
| **B8** | `chv-nwd` runs as non-root `chv` with `CAP_NET_ADMIN CAP_NET_RAW CAP_SYS_ADMIN`. dnsmasq binds the DHCP server socket on UDP/67; `net.ipv4.ip_unprivileged_port_start` is 1024, so every spawn exits `failed to bind DHCP server socket: Permission denied`. The documented DHCP path is dead even after the B4 lease-file fix. | **blocker** for the documented network profile |
| **B9** | `TopologyTable` is in-memory only. After a documented nwd restart, a policy update fails `set_firewall_policy failed: not found: topology <id> (NOT_FOUND)` and the operation ends `DISPATCH_FAILED`, even though the bridge, TAPs, and nft table still exist. | **blocker** (failed documented recovery, plan §6.4/§6.9) |

Two follow-ups were found while reviewing the fixes and are included in rc.8:

- DHCP MAC→IP reservations lived under `/run/chv/nwd`, which systemd's
  `RuntimeDirectory=` wipes on every nwd stop/restart. A restarted dnsmasq
  therefore stopped reserving the Core-assigned address; a DHCP guest could
  renew onto a pool address with no matching firewall policy.
- A durable journal or reservation set from a deleted deployment would
  survive `--wipe` and package removal, so a clean install could replay the
  previous run's bridges and reservations.

The detailed evidence is in
[`01-rc6-blockers.md`](../evidence/production-readiness/v0.4.0/field-qualification/01-rc6-blockers.md).

### 2.1 Fixes

- **B8 — bind the DHCP server port.** The nwd unit's
  `AmbientCapabilities`/`CapabilityBoundingSet` now include
  `CAP_NET_BIND_SERVICE`; the dnsmasq child inherits it and it grants nothing
  beyond binding privileged ports. dnsmasq start is a hard failure in
  `ensure_topology`: an apply that reports success with no DHCP server is the
  silent-success class behind B4/B8. The unit also creates the durable state
  directories (`0700 chv:chv`) before `ExecStart`.
- **B9 — durable bridge-only topology journal.**
  `crates/chv-nwd-core/src/topology_store.rs` atomically persists the exact
  `TopologySpec` protobuf under `/var/lib/chv/nwd/topologies/<network_id>.pb`
  after a successful apply, removes it on delete, and `NetworkServer::serve`
  replays every entry before binding its socket. A corrupt or ambiguous entry
  fails startup loudly instead of serving a partial table. Fabric topologies
  are deliberately **not** journaled: the stretched-L2 fabric is design-only
  and its provider owns its durable surface.
- **B9 — the policy guard is durable too.** Recovering the topology is not
  enough for plan §6.4 ("policy and bridge re-materialize"): nftables survives
  a process restart but not a host reboot, and the in-memory policy record is
  what re-scopes the interface guard when a NIC attaches. The last requested
  firewall/NAT policy and version are journaled under
  `/var/lib/chv/nwd/policies/<network_id>.json`, restored and re-applied
  fail-closed before serving, and removed on topology delete. Without this, a
  restart followed by an attach could leave the new tap outside CHV
  default-deny (the base hooks are `policy accept`; only the guard dispatches
  guest traffic into the policy chains). A payload the engine can never apply
  (malformed JSON, unknown action/protocol, IPv6 or `+`-prefixed CIDRs, a
  range nft rejects under every reading — the BFF stores `nat_rules` verbatim,
  so nwd is the only validator) is now rejected at the RPC boundary **before**
  it is journaled, because recovery replays the journal fail-closed; an
  unapplicable entry would otherwise crash-loop the daemon and only manual
  file surgery could clear it. A rejected payload leaves a rejection marker in
  memory (never in the journal) so the attach-time guard refresh refuses the
  NIC instead of proceeding with no policy, matching rc.7's fail-closed
  outcome, and the last valid journaled policy survives the rejected update.
  The gate is IPv4-only and canonicalizes the rc.7-storable numeric forms
  (leading-zero decimals, which nft may read as octal; `+`-prefixed ports,
  which nft rejects; and non-canonical CIDR prefixes) before rendering, so a
  stored rc.7 ruleset keeps enforcing a defined rule instead of failing
  dispatch. Where rc.7 accepted a non-canonical numeric form, rc.8 enforces
  the decimal value the operator wrote (e.g. `0443` → 443, `0100-0200` →
  100-200); a mixed-radix range that is reversed decimally but was applied by
  nft renders nft's values (`0100-99` → `64-99`) to preserve rc.7
  enforcement, and a form rc.7 could not apply (`+443`, `600-0777`) is now
  applied at its decimal meaning. The BFF save gate requires canonical forms for new saves and
  rejects a `dest_port` on a protocol without ports; nwd keeps applying such a
  legacy rc.7 rule with the port ignored and logs a warning, and renders
  `sctp dport` when canonical instead of silently dropping the constraint. If
  a persisted entry still cannot be re-applied, startup fails with an error
  naming the exact journal file so the operator has a documented recovery.
- **B9 — fabric overlay changes cannot add an unguarded interface.** A fabric
  apply grafts a consumer veth into the tenant bridge, and only the guard set
  dispatches guest traffic into the policy chains (the base hooks are
  `policy accept`). If the network's last firewall/NAT save was rejected, an
  overlay update or a fabric-carrying ensure now refuses before touching the
  datapath. If a rejection races a post-graft guard refresh, the handler
  removes the overlay, resets the bridge MTU, clears the persisted fabric
  generation, and reports that the overlay was rolled back; retry with the
  latest plan. If the removal itself fails, the error says the veth may
  remain grafted and unguarded. If the removal succeeds but the bridge-MTU
  reset fails, the error says the overlay was rolled back while the MTU may
  remain at the fabric value. The rollback is operator-visible: it tears down
  the network's fabric overlay rather than leaving a new veth outside the
  guard set.
- **B9 — agent startup replay closes the upgrade gap.** The rc.7 → rc.8
  upgrade starts with an empty journal. The agent now asks nwd which
  topologies it already owns and re-ensures only the distinct bridge-only
  networks referenced by a live Core VM that nwd does **not** own, with
  bounded retries, before serving. Skipping an already-owned network matters:
  nwd recovers its journal before serving, and a VM definition is a
  create-time snapshot, so replaying it could roll a later CIDR/gateway change
  back. This seeds the journal for later nwd-only restarts. A failed ownership
  query falls back to replaying every network (the upgrade case); the replay
  is best-effort and cannot block agent startup.
- **Persistent DHCP reservations.** The `dhcp-hostsfile` now lives under
  `/var/lib/chv/nwd/dhcp/`, is created only when absent, and is removed only
  by topology teardown. A failed reservation unlink fails the delete closed
  (the idempotent retry clears it) rather than leaving a MAC→IP map that a
  re-created network would inherit. Lease files intentionally stay under
  `/run` (B4).
- **Durable state follows teardown.** `install.sh --wipe`/re-run cleanup, the
  packaged `preremove.sh` (remove/purge only, never upgrade), and
  `dev-install.sh` remove `${CHV_DATA_DIR:-/var/lib/chv}/nwd`.

## 3. What changed since v0.4.0-rc.7

### Product

- `packaging/systemd/chv-nwd.service` and
  `docs/examples/systemd/chv-nwd.service`: `CAP_NET_BIND_SERVICE` in the

  `/var/lib/chv/nwd/dhcp` (B8/B9).

  id validation, fail-closed `load_all`, directory fsync, and tests (B9).
- `crates/chv-nwd-core/src/policy_store.rs` (new): atomic JSON journal for the
  last requested firewall/NAT policy, fail-closed load, and tests (B9
  follow-up).
- `crates/chv-nwd-core/src/{handlers,server}.rs`: journal on successful
  ensure, remove on delete, repair on the idempotent path, recover topology
  **and policy** before serving, and re-apply the recovered guard set (B9).
- `crates/chv-nwd-core/src/{executor,dhcp}.rs`: persistent DHCP hostsfile,
  dnsmasq start as a hard failure, and reservation cleanup on topology
  teardown (B8/B9 follow-ups).
- `crates/chv-agent-core/src/network_replay.rs` (new) and
  `cmd/chv-agent/src/main.rs`: startup replay from the Core VM set in both
  core-managed and core-native startup, skipping networks nwd already owns

## 4. If you already run rc.7 or earlier

- **Upgrade order matters.** rc.7 → rc.8 requires `chv-nwd` to be restarted
  before (or with) `chv-agent`, so the agent's startup replay reaches rc.8
  nwd and seeds the journal. `chv-agent.service` already orders
  `After=chv-nwd.service`; `systemctl restart chv-nwd chv-agent` is correct.
  The package scripts deliberately do not restart services.
- **The first policy update after the upgrade needs a running rc.8 agent.**
  If the agent is not restarted, rc.8 nwd starts with an empty journal and
  cannot recover the rc.7 topology table until an ensure arrives. Restart
  both units once, then verify a policy update succeeds.
- **One-time DHCP reservation gap.** Reservations written by rc.7 under
  `/run/chv/nwd` are not migrated. The upgrade restart re-creates the
  topology but not the per-NIC reservations; a DHCP guest keeps its current
  lease until renewal, and a VM re-create (or a clean rc.8 install)
  repopulates the persistent file. The field upgrade drill uses cloud-init
  static addressing for the guest; the reservation-survives-nwd-restart
  contract is exercised on the clean install.
- **Fabric topologies are not journaled.** The stretched-L2 fabric is
  design-only in this release. Do not expect an nwd restart to rebuild a
  fabric overlay; the provider owns that durable surface. Bridge-only
  topologies are the supported profile.
- **rc.6 and earlier:** follow the rc.7 release notes §4 for the legacy
  `chvbr0` cleanup and the VM delete/recreate rule. rc.8 does not change
  those migrations.
- **`install.sh --wipe` remains destructive by design.** It removes the
  node's identity-bound Core authority state, the control-plane database, VM
  runtime state, images, UI tree, host network state, and now the durable
  nwd network state. A plain re-run without `--wipe` still refuses to proceed
  when persistent data is present.

## 5. Known limitations

The authoritative list is the
[support matrix](v0.4.0-rc.8-support-matrix.md) and
[`DEPLOYMENT-ARCHITECTURE.md` §9](../DEPLOYMENT-ARCHITECTURE.md#9-known-boundaries-and-residual-risk).

- **Single host only.** Multi-host control-plane/agent dispatch is
  architecturally absent; ADR-029 is accepted but not implemented. The
  VXLAN/WireGuard fabric is design-only.
- **rc.8 evidence boundary.** At tag time the B8/B9 and follow-up fixes are
  covered by targeted Rust tests, packaging/architecture contract tests,
  `cargo fmt`, and clippy `-D warnings`. The rc.8 artifact, once published,
  has **no post-publication lane and no field day**; the rc.7 → rc.8 upgrade
  (nwd then agent), clean install, documented start with a guest DHCP lease
  and `login:` console, a policy change plus nwd restart with the reservation
  surviving, and two consecutive `--wipe` installs must be repeated after
  publication before the window opens. Nothing in this note claims that run.
- **VMM/serial containment.** Cloud Hypervisor is pinned to v53.0. The silent
  serial-manager thread death and the adopted-VM stop wedge are contained,
  not cured; re-verify at every VMM upgrade (#345 root / #409).
- **Firewall/NAT rule CIDRs are IPv4 only.** The nwd engine renders rules
  with `ip saddr`/`ip daddr`, so the BFF save gate and the nwd RPC both reject
  IPv6 CIDRs. Accepting one would journal a payload that can never apply and
  crash-loop fail-closed recovery. IPv6 matching is not claimed in rc.8.
- **Migration is stop-the-world only.** Pause-first is required; live
  concurrent-write migration is not claimed. One multi-volume
  convergence-skew residual is disclosed (#582).
- **Backup/restore is hard-fenced.** All backup/restore routes return
  `501 NOT_IMPLEMENTED`; there is no DR claim or restore validation.
- **Storage.** Local file and LVM are qualified; Ceph RBD and iSCSI are coded
  but unqualified. K8s/CNI, Docker-forwarded, and multi-bridge coexistence are
  not claimed.
- **Upgrade.** Package upgrade is CI-verified; rolling node upgrade is absent
  and downgrade is unsupported. No rc.8 post-publication lane has run at tag
  time.
- **Scale.** No concurrency, density, throughput, or requests-per-second
  claim. M4.8 numbers are single-host baselines.
- **Hardware minimums.** "4 cores / 8 GB RAM / 50 GB disk" is an unevidenced
  recommendation, not a qualification-backed envelope.

## 6. Upgrade and verification notes

The release artifact is the published tarball's `scripts/install.sh`
(release-directory mode) and the published `.deb` set. Package versions carry
`~rc.8`; the node row reports the base `0.4.0`, so the artifact is
discriminated by the package version and the binaries' commit banner.

Before the field window opens, the campaign must repeat, on `field-host-1`:

1. `rc.7 → rc.8` package upgrade (or `v0.3.0 → rc.8`), restarting `chv-nwd`
   before/with `chv-agent`; verify configuration, database, certificates,
   operator account, and a running VM survive, and that a policy update
   succeeds after the restart.
2. Uninstall/purge, then a clean rc.8 tarball install.
3. A documented start with the seeded network: `start_http=200`, the VMM
   reports `Running`, `config.net` carries the requested NIC, the guest
   obtains a DHCP lease from `/run/chv/nwd/dnsmasq-<id>.leases`, and the
   console reaches `login:`.
4. A policy change and an nwd restart; the guest keeps its lease and
   connectivity, the persistent reservation under
   `/var/lib/chv/nwd/dhcp/` still names its MAC→IP pair, and the firewall/NAT
   guard recovers (a policy update and a NIC attach after the restart both
   succeed and re-scope).
5. Two consecutive `--wipe` installs; both reach `TenantReady`.

Only then does the 21–30 day field window start. These are planned steps, not
results; this note does not claim them.
