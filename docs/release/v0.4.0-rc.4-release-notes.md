## 1. This is a release candidate, not stable

This build is for evaluation and staged rollout with an operator who has read
the support matrix and the known limitations. It does **not** claim multi-host
operation, HA/control-plane failover, live (concurrent-write) migration,
backup/restore as DR, Ceph/iSCSI storage, Volvisor-backed storage, RPM
behavior on a real host, arm64, or any scale figure.

No field deployment has happened yet. The field-qualification campaign
([plan](../plans/2026-11-05-v0.4.0-field-qualification.md),
[profile](../DEPLOYMENT-ARCHITECTURE.md) §5 UC-11) starts from a clean rc.5
install (rc.4's quick installer is defective) and runs for 21–30 days. A
passing field campaign is an input to the stable decision, not a
pre-approval.

## 2. Why rc.4 exists: the quick-install half of the blocker

`v0.4.0-rc.3` fixed the #722 data-loss defect in `scripts/install.sh`
(tarball, package, and the qualified install path) and its post-publication
lane passed all four legs. But the **quick installer at the rc.3 tag still
seeded the admin against a live control plane**, so the same defect remained
on the `scripts/quick-install.sh` path. rc.3 is therefore not the final RC.

**What happened.** After `start_services`, `seed_admin_user` ran an
idempotency `SELECT` and an `INSERT` with the `sqlite3` CLI while
`chv-controlplane` was running. When the CLI was the last connection to
close, it checkpointed and unlinked `controlplane.db-wal`/`-shm`; the live
service kept the now-unlinked inodes open. Every API write it acknowledged
afterwards went into the unlinked WAL and disappeared when the process exited
— on a restart, an upgrade, or a reboot.

**Reproduction on the published rc.3 quick installer.** On a clean Ubuntu
noble nspawn guest, `scripts/quick-install.sh --version 0.4.0-rc.3` returned
`rc=0`, and then:

- `/proc/<chv-controlplane>/fd` showed four `controlplane.db-wal (deleted)`
  and one `controlplane.db-shm (deleted)` handle;
- `POST /v1/auth/change-password` returned 200 and the new password logged in
  live;
- `POST /v1/users/create` returned 200 and the user was listed;
- after `systemctl restart chv-controlplane`, the rotated password returned
  401 and the created user was gone.

This is the same mechanism as the #722 defect, reproduced independently on
the rc.3 quick-install path.

**The fix (#725).** `chv_sqlite_offline` stops `chv-controlplane`, runs the
direct SQLite read/write as the `chv` service user, restarts the service, and
waits for `/health`. It is used for the admin idempotency check and the admin
`INSERT`, matching `scripts/install.sh`. `wait_for_enrollment` now queries a
snapshot copy of the database instead of opening the live WAL from a second
process. A failed check or restart is fatal, so an install can no longer
report success with the control plane down.

With the fix, the same local guest showed no `(deleted)` WAL handles, and the
rotation and created user survived **two** control-plane restarts.

## 3. What changed since v0.4.0-rc.3

### Product

- **Quick installer only (#725).** The write path described in §2.
  `scripts/quick-install.sh` is fetched from the repository at the tag; it is
  not part of the release tarball or the `.deb`/`.rpm` payloads. No Rust
  crate, migration, unit file, or package payload changed.

### Qualification (not product behavior)

- **Candidate-mode quick leg (#725).** `fresh-host.sh` gained
  `--quick-install-candidate`; the workflow sets it when the dispatched tag
  equals the quick-install version. A post-publication run that installs
  `0.4.0-rc.4` (the binaries report the base `0.4.0`) now runs
  `check_bringup` **and** `check_credential_persistence`.
- **Why rc.3's lane missed it.** The rc.3 post-publication run
  ([42139285660](https://github.com/o3kio/chv/actions/runs/42139285660))
  compared `QUICK_VERSION=0.4.0-rc.3` with `CANDIDATE_VERSION=0.4.0`; the
  release sorted as "previous", so the quick leg took the weaker
  previous-release branch and never ran the persistence gate. The install
  path itself was still covered: the rc.3 `install-tarball` leg ran the
  persistence gate and passed (that path uses the fixed `scripts/install.sh`).
- **Offline invariants.** The quick installer's admin check, admin seed, and
  enrollment snapshot are pinned to the offline/snapshot helpers; reverting
  only the idempotency read now fails the suite.

## 4. If you already run an earlier release

- **`v0.4.0-rc.2` and earlier:** the tarball/package install path can lose
  API writes from the install process lifetime. Do not use rc.2 for a new
  install; verify accounts and configuration after upgrading.
- **`v0.4.0-rc.3`:** the tarball/package install path is fixed, but the
  **quick installer** still has the defect. Do not use the rc.3 quick
  installer for a new install.
- The seeded bootstrap password in `/etc/chv/initial_admin_password` remains
  the recovery path if a rotation was lost; the first-login rotation is
  re-prompted when `must_change_password=1`.
- Upgrading fixes the installer and the running process's durability. It
  cannot restore writes that were already lost.

## 5. Known limitations

The authoritative list is the
[support matrix](v0.4.0-rc.4-support-matrix.md) and
[`DEPLOYMENT-ARCHITECTURE.md` §9](../DEPLOYMENT-ARCHITECTURE.md#9-known-boundaries-and-residual-risk).

- **Single host only.** Multi-host control-plane/agent dispatch is
  architecturally absent; ADR-029 is accepted but not implemented. The
  VXLAN/WireGuard fabric is design-only.
- **VMM/serial containment.** Cloud Hypervisor is pinned to v53.0. The silent
  serial-manager thread death and the adopted-VM stop wedge are contained,
  not cured; re-verify at every VMM upgrade (#345 root / #409).
- **Migration is stop-the-world only.** Pause-first is required; live
  concurrent-write migration is not claimed. The underlying stord primitive
  assumes a quiescent source. One multi-volume convergence-skew residual is
  disclosed (#582).
- **Backup/restore is hard-fenced.** All backup/restore routes return
  `501 NOT_IMPLEMENTED`; there is no DR claim or restore validation.
- **Storage.** Local file and LVM are qualified; Ceph RBD and iSCSI are coded
  but unqualified. K8s/CNI, Docker-forwarded, and multi-bridge coexistence are
  not claimed.
- **Upgrade.** Package upgrade is CI-verified; rolling node upgrade is absent
  and downgrade is unsupported. The fresh-host install → operate → package
  upgrade → uninstall path (#666) and the published quick installer (#556)
  passed on `v0.4.0-rc.1` in a clean container (run
  [42042149140](https://github.com/o3kio/chv/actions/runs/42042149140)).
  rc.3's post-publication lane
  ([42139285660](https://github.com/o3kio/chv/actions/runs/42139285660)) is
  green on the fixed tarball/package path, but its quick leg did not run the
  persistence gate and the quick installer it exercised is defective. The
  rc.4 post-publication lane
  ([42148690329](https://github.com/o3kio/chv/actions/runs/42148690329))
  passed tarball, packages, and upgrade but failed the quick leg (no enrolled
  node); the rc.4 quick installer is defective and fixed in rc.5. None of
  this is bare-metal or cloud-VM evidence.
- **Scale.** No concurrency, density, throughput, or requests-per-second
  claim. M4.8 numbers are single-host baselines.
- **Hardware minimums.** "4 cores / 8 GB RAM / 50 GB disk" is an unevidenced
  recommendation, not a qualified envelope.
- **Residual operations.** M2.5 delete retention (BFF/CP rows, VM dir, volume
  row, backing file persist); JWT/encryption key coupling (#336); the audit
  crash window (#706); and distinct `metrics_bind` values are required when
  running more than one stord per host.
  #711 (detached-open session) is exercised by the rc.2 lane's F7 sweep
  (base VM created before an agent restart, deleted after; 0 sessions left).
  #709 (first-enrollment bootstrap audit gap) is asserted by the rc.2 lane's
  deploy leg (`node_bootstrap_results.success = 1` on the issued identity).
  Sessions orphaned by a crash on a **pre-upgrade** stord (the old detach left
  `runtime_status = "open"`) are not reclaimed by the VM-delete sweep, because
  they are indistinguishable from a live opened-but-attach-pending session;
  `DeleteVolume` closes every session with no attached VM before destroying,
  so these orphans clear on volume destroy. A session still attached to a VM
  keeps the destroy refusal; if a failed drain left a dead VM's id on the row,
  detach that volume from the named VM before attempting the delete — a failed
  delete attempt tombstones the volume `'Deleting'`, which refuses the detach
  and replays the failure on retry. The detach mutation honors an explicit
  `vm_id`, so it can name the dead VM after the control plane cleared the
  attachment.
- **UI evidence scope.** The UI was not re-qualified end-to-end in prompt-04;
  scenario evidence is chvctl/BFF/API-driven (with the network-policy path
  driven through the BFF in the 2026-11-04 lane).
- **Volvisor is design-only.** ADR-028 selects it as the future storage
  authority; runtime integration is pending. The qualified path remains
  `chv-stord`.

## 6. Upgrade notes

- Back up the control-plane SQLite database before upgrading; migrations are
  forward-only and **downgrade is unsupported**. The manual rollback procedure
  is in [`package-contract.md`](package-contract.md).
- Package conffiles are `config|noreplace`; services are **not** restarted
  automatically on upgrade. Restart the units explicitly and confirm the
  four services are healthy.
- Verify the node row reports the new version after the upgrade and the agent
  reports the new version. If it still lags, record it as an operational
  defect rather than assuming the upgrade failed.
- Run more than one stord per host only with distinct `metrics_bind` values;
  the default `127.0.0.1:9101` is not multi-instance-safe.
- Re-save networks after upgrade if they carry pre-#365 NULL gateways or
  pre-#369 dialect rules; pre-#481 imported/template volumes remain
  ownerless/admin-only.
- Migration operators must pass `--pause-first` (`chvctl`) or use the WebUI's
  mandatory pause-first control; the live path is rejected by design.
- **Quick-install users on rc.1–rc.4:** install **rc.5** and re-run it (or
  upgrade through the packages), then verify the admin password, users,
  configuration, and that the node appears in `/v1/nodes`. The rc.1–rc.4
  quick installers can lose acknowledged writes (rc.1–rc.3), fail to enroll
  (rc.4), or fail to re-enroll (rc.1–rc.4); rc.5 fixes all three.
