## 1. This is a release candidate, not stable

This build is for evaluation and staged rollout with an operator who has read
the support matrix and the known limitations. It does **not** claim multi-host
operation, HA/control-plane failover, live (concurrent-write) migration,
backup/restore as DR, Ceph/iSCSI storage, Volvisor-backed storage, RPM
behavior on a real host, arm64, or any scale figure.

No field-qualification campaign has run yet. The rc.5 pre-window drills on
`field-host-1` (§2) are rc.5 evidence and do not qualify rc.6. The campaign
([plan](../plans/2026-11-05-v0.4.0-field-qualification.md), profile in
[`DEPLOYMENT-ARCHITECTURE.md`](../DEPLOYMENT-ARCHITECTURE.md) §5 UC-11) starts
from a clean rc.6 install and runs for 21–30 days. A passing field campaign is
an input to the stable decision, not a pre-approval.

## 2. Why rc.6 exists: rc.5 failed the restart drill

rc.5's post-publication container lane passed all four legs, but the plan's
§6.4 restart drill is a field-host drill on real VMs. On the published rc.5
installation on `field-host-1`, three independent runs reproduced a
blocker-class failure (#732):

1. `systemctl restart chv-agent` with one running VM took **76 s**, exceeded
   `TimeoutStopSec=75`, and systemd SIGKILLed the cgroup. The
   `cloud-hypervisor` process died. The API still reported
   `power_state=Running` because desired state took precedence, and the node
   went `Degraded` then `Failed`.
2. A direct `SIGTERM` left the main thread in a runtime-shutdown futex wait
   and one Tokio worker blocked in a serial-socket read. An external
   `shutdown(SHUT_RD)` on the console socket released it immediately; even
   then, systemd's `KillMode=mixed` killed the VMM when the main process
   exited.
3. A plain `systemctl stop` followed by `systemctl start` (no crash, no VM
   needed) removed `/run/chv/stord` and `/run/chv/nwd` with the agent's
   `RuntimeDirectory=chv`. The still-running daemons kept their unlinked
   sockets and ports 9101/9102; the supervisor spawned duplicates that died
   with `Address already in use`; the node stayed `Failed`/`Degraded` and
   `CreateVm` was refused with `must be TenantReady`. It did not self-heal
   after more than 60 s.

### 2.1 Root causes (all in rc.5)

- **A — `KillMode=mixed`.** systemd SIGKILLs the remaining cgroup when the
  main process exits. A running `cloud-hypervisor`, as a child of
  `chv-agent`, can never survive an agent restart, even with a clean exit.
- **B — the drain never unblocks the blocking reader.** The graceful shutdown
  half-closed each serial console with `SHUT_WR` but left the dedicated
  `spawn_blocking` reader waiting for data. With a live VMM the peer keeps the
  socket open, so the read never returned and Tokio's runtime drop waited
  until systemd's timeout.
- **C — `RuntimeDirectory=chv`.** systemd removes the directory recursively on
  every stop/restart, deleting the separately managed `chv-stord`/`chv-nwd`
  runtime directories. Their sockets are unlinked while the processes keep
  listening, so the supervisor cannot adopt them and its duplicate spawns
  fail on the metrics ports.

### 2.2 The fix (#732)

- `packaging/systemd/chv-agent.service` and its
  `docs/examples/systemd` copy now use `KillMode=process` and
  `RuntimeDirectory=chv/agent`. VMMs outlive the agent and are adopted on the
  next start; only the agent's own runtime leaf is removed. `TimeoutStopSec`
  stays at 75 s.
- The shutdown drain now waits for a bounded settle — a 200 ms floor,
  consecutive empty receive-queue probes on the fast path, and a shared 1 s
  deadline — and then issues `shutdown(SHUT_RD)` so the blocking readers see
  EOF. The empty-probe streak is a fast-path signal, not proof that the peer
  stopped writing; a late write after the shut-down remains possible and
  degrades to the pre-fix, `vm.reboot`-recoverable behavior.
- Pty-transport consoles, which have no `shutdown(2)`, poll the draining latch
  instead of staying parked.
- Regression tests cover the late-write window, the live-reader unblock, the
  Pty reader, and the unit contract.

### 2.3 Removal residue in the same window (blocker-class, §6.9)

Because VMMs now outlive the agent, every **final** removal path must stop
them explicitly. The rc.5 removal paths had no explicit VMM termination —
they relied on the agent's old `KillMode=mixed` cgroup kill, which rc.6
removes — and no teardown of the host network state nwd materializes outside
`/var/lib/chv`. Without that, an rc.6 uninstall would leave VMMs,
namespaces, tables, bridges, taps, and NAT rules behind: field-plan §6.9
"VM/process/volume/network residue that survives documented cleanup". A
live drill against the fix branch
(`scripts/quick-install.sh --uninstall --purge`) then confirmed the fixed
path removes the running VMM and all of that state. rc.6 addresses it:

- package remove/purge, `scripts/install.sh --wipe` and re-run cleanup, and
  `scripts/quick-install.sh --uninstall` terminate CHV-owned
  cloud-hypervisor processes before the binaries and data go away;
- the same paths (and `preremove.sh` on remove/purge, never on upgrade) tear
  down the host state nwd materializes outside `/var/lib/chv`, for hex and
  operator-chosen ids, including the literal `default` network
  (`ns-default`, `chv-default`, `chvbr0`);
- a bridge that is already gone is handled by unioning every CIDR source: the
  live route, every `! -o <bridge>` rule (live `iptables -S` and the
  persisted file), and the database `network_desired_state.cidr` /
  `INSTALL_CHV_BRIDGE_CIDR` baseline. The database hint is regex-gated to
  `^[0-9a-fA-F:.]+/[0-9]{1,3}$` before it can reach `iptables`; a single
  non-IP token is still passed as one quoted argument and rejected there, so
  nothing is deleted or executed;
- every final path clears stale failed unit state; `install.sh --wipe` and
  `quick-install.sh --uninstall` additionally remove the installer-owned UI
  tree, migrations, and nginx site.
- A sandboxed test runs all three shipped removal copies (including
  `preremove.sh` under dash and bash `pipefail`) against fake host tools and
  proves non-CHV objects survive. A failing `nft`/`ip`/`sort` cannot abort the
  teardown before the baseline bridge and orphan-table sweep.

> **The removal is VMM-level.** The teardown sends `SIGTERM` then `SIGKILL`
> (after 10 s) to the VMM process; it is **not** a guest-OS shutdown. If the
> guests must flush their own buffers, stop them through the API before
> removal.

## 3. What changed since v0.4.0-rc.5

### Product

- **Agent unit** (`packaging/systemd/chv-agent.service`, mirrored in
  `docs/examples/systemd/chv-agent.service`): `KillMode=process`,
  `RuntimeDirectory=chv/agent`. `ExecStopPost` still removes only the agent
  API socket; tmpfiles still create `/run/chv/agent` 0775 and
  `/run/chv/core` 0700.
- **Agent runtime** (`crates/chv-agent-runtime-ch/src/process.rs`): the
  bounded drain and `SHUT_RD` unblock, and the Pty draining latch. No API,
  schema, migration, configuration-format, or storage-format change.
- **Removal** (`scripts/install.sh`, `scripts/quick-install.sh`,
  `packaging/scripts/preremove.sh`): VMM termination, host network teardown,
  CIDR recovery, orphan-table sweep, and stale-unit cleanup as described in
  §2.3.
- **Tests** (`tests/test_cellhv_core_packaging.py`,
  `tests/scripts/qual-harness-invariants.sh`): 14 packaging tests (up from
  5), the Rust drain/live-reader/Pty tests, and 174 invariants. Each new
  regression test was mutation-verified against its fix.

### Documentation

- The field plan gains the rc.6 amendment; the rc.5 release notes and support
  matrix carry a superseded/defect banner (their tags are not rewritten).
- `README.md`, `docs/DEPLOYMENT.md`, and `docs/DEPLOYMENT-ARCHITECTURE.md`
  point at rc.6 and state the rc.6 evidence boundary.
- `docs/install/uninstall.md` documents the new VMM-terminating removal
  paths (merged with #733).

### Not changed

No control-plane lifecycle, migration, storage, network-policy,
authentication, or UI product code changed. The rc.6 delta is the agent restart/drain path, the
agent unit, removal scripts, tests, and documentation.

## 4. If you already run an earlier release

- **`v0.4.0-rc.5`:** do not use it as the stable base. On rc.5,
  `systemctl restart chv-agent` with a running VM kills the VMM; a plain
  stop/start can wedge the node. Upgrade to rc.6 before running the field
  workload.
- **`v0.4.0-rc.4` and earlier quick installs:** the quick installer can
  complete with no enrolled node (rc.4) or destroy the enrolled identity on a
  re-run (rc.1–rc.4). Do not use those quick installers for a new install or
  an upgrade. rc.5 and rc.6 retain the #727 fixes.
- **`v0.4.0-rc.2` and earlier tarball/package installs:** the install path
  could lose API writes from the install process lifetime. Verify accounts
  and configuration after upgrading.
- If a quick-install node never enrolled, install rc.6 and re-run it (or use
  the tarball/package path). rc.5's and rc.6's quick installers preserve a
  usable enrolled identity on re-run.
- The seeded bootstrap password in `/etc/chv/initial_admin_password` remains
  the recovery path if a rotation was lost; the first-login rotation is
  re-prompted when `must_change_password=1`.
- Upgrading fixes the runtime and removal paths. It cannot restore writes or
  VMs that were already lost.

## 5. Known limitations

The authoritative list is the
[support matrix](v0.4.0-rc.6-support-matrix.md) and
[`DEPLOYMENT-ARCHITECTURE.md` §9](../DEPLOYMENT-ARCHITECTURE.md#9-known-boundaries-and-residual-risk).

- **Single host only.** Multi-host control-plane/agent dispatch is
  architecturally absent; ADR-029 is accepted but not implemented. The
  VXLAN/WireGuard fabric is design-only.
- **Restart/heal evidence is not a real-KVM lane on rc.6.** The unit half of
  the rc.6 fix is covered by a pre-publication field-host drill (the
  candidate unit on the published rc.5 binary: VMM survived with the same
  PID, stord/nwd PIDs and socket inodes were unchanged, the agent adopted the
  VM, zero duplicate spawns, `TenantReady`/`Healthy` at +1 s). The drain fix
  is covered by the Rust tests. No rc.6 real-KVM or post-publication lane is
  claimed at tag time.
- **VMM/serial containment.** Cloud Hypervisor is pinned to v53.0. The silent
  serial-manager thread death and the adopted-VM stop wedge are contained,
  not cured; re-verify at every VMM upgrade (#345 root / #409).
- **Migration is stop-the-world only.** Pause-first is required; live
  concurrent-write migration is not claimed. One multi-volume
  convergence-skew residual is disclosed (#582).
- **Backup/restore is hard-fenced.** All backup/restore routes return
  `501 NOT_IMPLEMENTED`; there is no DR claim or restore validation.
- **Storage.** Local file and LVM are qualified; Ceph RBD and iSCSI are coded
  but unqualified. K8s/CNI, Docker-forwarded, and multi-bridge coexistence are
  not claimed.
- **Upgrade.** Package upgrade is CI-verified; rolling node upgrade is absent
  and downgrade is unsupported. The rc.5 container lane
  ([42159563210](https://github.com/o3kio/chv/actions/runs/42159563210))
  remains the evidence for the #727 installer fixes; it does not cover the
  rc.6 runtime or the rewritten removal paths. The rc.6 post-publication lane
  has not run at tag time and is not claimed.
- **Scale.** No concurrency, density, throughput, or requests-per-second
  claim. M4.8 numbers are single-host baselines.
- **Hardware minimums.** "4 cores / 8 GB RAM / 50 GB disk" is an unevidenced
  recommendation, not a qualified envelope.
- **M2.5 delete retention (pre-existing, disclosed).** `vm delete` removes
  authority-side state, but the BFF list row, CP row, VM directory, volume
  row, and backing file persist; the API/UI can keep returning the deleted VM
  with its last desired power state. The truthful delete signal is the
  task/operation result. This is not part of the #732 fix and is not a
  blocker; the field profile must disclose it.
- **Removal is not a guest shutdown** (see §2.3).
- **Residual removal/restart boundaries:** the late serial write after
  `SHUT_RD` (bounded, `vm.reboot`-recoverable); VMM adoption is matched by the
  CHV runtime path under `/var/lib/chv/agent/vms`, so a custom `CHV_DATA_DIR`
  is not covered; `INSTALL_CHV_BRIDGE_NAME` overrides are covered by the
  baseline fallback, but a custom baseline CIDR outside the installer/database
  sources is not; `preremove.sh` invoked without systemd tears down host state
  but can leave already-running stord/nwd processes (the package path uses
  systemd); a PID-reuse window exists between identifying and signalling a
  VMM; netns-only discovery is deliberately conservative (`default` plus
  legacy hex ids) and can miss an operator id that has no database row, nft
  table, or bridge; `install.sh`'s wipe path still carries the pre-existing
  `/24` hardcode for the baseline CIDR. These are disclosed, not silently
  fixed.
- **Residual operations.** JWT/encryption key coupling (#336); the audit
  crash window (#706); distinct `metrics_bind` values are required when
  running more than one stord per host. #711 (detached-open session) is
  exercised by the rc.2 lane's F7 sweep; #709 (first-enrollment bootstrap
  audit gap) is asserted by the rc.2 lane's deploy leg. Sessions orphaned by a
  crash on a **pre-upgrade** stord are not reclaimed by the VM-delete sweep;
  `DeleteVolume` closes every session with no attached VM before destroying,
  so these orphans clear on volume destroy. The full wording is in §9 of the
  architecture document.
- **UI evidence scope.** The UI was not re-qualified end-to-end in prompt-04;
  scenario evidence is chvctl/BFF/API-driven.
- **Volvisor is design-only.** ADR-028 selects it as the future storage
  authority; runtime integration is pending. The qualified path remains
  `chv-stord`.

## 6. Upgrade notes

- Back up the control-plane SQLite database before upgrading; migrations are
  forward-only and **downgrade is unsupported**. The manual rollback procedure
  is in [`package-contract.md`](package-contract.md).
- Package conffiles are `config|noreplace`; services are **not** restarted
  automatically on upgrade. Restart the units explicitly and confirm the
  four services are healthy.
- **Restart the agent only after the new unit is installed.** The rc.6 unit is
  what makes running VMs survive the restart; on an rc.5 unit the restart
  still kills them.
- Verify the upgrade completed and the agent reports the new build. The node
  row reports the base `0.4.0`, which does not change between rc.5 and rc.6;
  discriminate the RC by the package version `0.4.0~rc.6` and the commit
  banner printed by the binaries. If it still lags, record it as an
  operational defect rather than assuming the upgrade failed.
- After upgrading, verify exactly one `chv-stord` and one `chv-nwd`, node
  `TenantReady`/`Healthy`, and each running VMM still present with the same
  PID.
- Re-save networks after upgrade if they carry pre-#365 NULL gateways or
  pre-#369 dialect rules; pre-#481 imported/template volumes remain
  ownerless/admin-only.
- Migration operators must pass `--pause-first` (`chvctl`) or use the WebUI's
  mandatory pause-first control; the live path is rejected by design.
- **Quick-install users on rc.1–rc.4:** install rc.6 and re-run it (or upgrade
  through the packages), then verify the admin password, users,
  configuration, and that the node appears in `/v1/nodes`.
- **Removing the deployment:** package remove/purge, `install.sh --wipe`, and
  `quick-install.sh --uninstall` now stop CHV VMMs and delete host network
  state. Package removal preserves `/var/lib/chv`, `/etc/chv`, and
  `/var/log/chv`; the wipe/uninstall paths remove the installer-owned trees.
  See [`docs/install/uninstall.md`](../install/uninstall.md).
