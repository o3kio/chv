## 1. This is a release candidate, not stable

This build is for evaluation and staged rollout with an operator who has read
the support matrix and the known limitations. It does **not** claim multi-host
operation, HA/control-plane failover, live (concurrent-write) migration,
backup/restore as DR, Ceph/iSCSI storage, Volvisor-backed storage, RPM
behavior on a real host, arm64, or any scale figure.

No field deployment has happened yet. The field-qualification campaign
([plan](../plans/2026-11-05-v0.4.0-field-qualification.md),
[profile](../DEPLOYMENT-ARCHITECTURE.md) §5 UC-11) starts from a clean rc.2
install and runs for 21–30 days. A passing field campaign is an input to the
stable decision, not a pre-approval.

## 2. What changed since v0.4.0-rc.1

- **Node version truth (#720).** The node API and cluster summary now report
  the agent version from the agent's periodic `ReportServiceVersions` report.
  Previously only enrollment wrote `nodes.agent_version`, so an in-place
  package upgrade could leave the node row showing the previous release while
  the running binaries reported the new one (observed on the rc.1 fresh-host
  run). The refresh is a no-op when the version is unchanged. A regression
  test reports rc.2 over a node seeded at rc.1 and reads the value back
  through `POST /v1/nodes`. This is the only product-code change since rc.1;
  the rest of the rc.2 delta is documentation, release preparation, and the
  qualification-harness corrections below.
- `node_inventory.chv_*_version` remains enrollment-time data and has no
  readers; the code records that boundary so a future reader refreshes it
  rather than reintroducing the lag.

### Qualification-harness corrections (not product behavior)

- The deploy leg now asserts that a successful first enrollment records the
  `node_bootstrap_results` row with `success = 1` on the issued identity
  (#709). The previous harness only checked that the one-time token was
  consumed, so a regression back to the pre-enrollment channel could have
  passed quietly.
- The m4.8 metric-cardinality verdict now compares the post-first-lifecycle
  warm sample to the at-rest sample instead of the pre-work P1 sample. The
  #702 registry families (`chv_vm_ops_total` keyed by `op`/`result`,
  `chv_vm_op_duration_seconds` keyed by `op`, and the gRPC
  service/method/status families) are fixed-label and materialize on first
  use. Stage A run 42055268623 recorded 29 series before any VM work and
  184 after the first lifecycles, then flat at 184 at mid-soak, soak end,
  and the at-rest window. The corrected check requires the at-rest count to
  be unchanged from the warm baseline and keeps the absolute cap (≤ 200).
  The full curve remains in `metrics-cardinality.txt`.

Nothing else in the supported envelope changed. The full rc.1 scope and
evidence remain in the
[rc.1 release notes](v0.4.0-rc.1-release-notes.md).

## 3. Known limitations

The authoritative list is the
[support matrix](v0.4.0-rc.2-support-matrix.md) and
[`DEPLOYMENT-ARCHITECTURE.md` §9](../DEPLOYMENT-ARCHITECTURE.md#9-known-boundaries-and-residual-risk).

- **Single host only.** Multi-host control-plane/agent dispatch is
  architecturally absent; ADR-029 is accepted but not implemented. The
  VXLAN/WireGuard fabric is design-only.
- **VMM/serial containment.** Cloud Hypervisor is pinned to v53.0. The silent
  serial-manager thread death and the adopted-VM stop wedge are contained,
  not cured; re-verify at every VMM upgrade (#345 root / #409).
- **Migration is stop-the-world only.** Pause-first is required; live
  concurrent-write migration is not claimed. The underlying stord primitive
  assumes a quiescent source. One multi-volume convergence-skew residual is
  disclosed (#582).
- **Backup/restore is hard-fenced.** All backup/restore routes return
  `501 NOT_IMPLEMENTED`; there is no DR claim or restore validation.
- **Storage.** Local file and LVM are qualified; Ceph RBD and iSCSI are coded
  but unqualified. K8s/CNI, Docker-forwarded, and multi-bridge coexistence are
  not claimed.
- **Upgrade.** Package upgrade is CI-verified; rolling node upgrade is absent
  and downgrade is unsupported. The rc.1 fresh-host install → operate →
  package upgrade → uninstall path and the published quick installer passed
  in a clean container (run
  [42042149140](https://github.com/o3kio/chv/actions/runs/42042149140)).
  The rc.2 post-publication fresh-host lane is run after publication and
  recorded in the living docs; it is not pre-claimed here. Neither is
  bare-metal or cloud-VM evidence.
- **Scale.** No concurrency, density, throughput, or requests-per-second
  claim. M4.8 numbers are single-host baselines.
- **Hardware minimums.** "4 cores / 8 GB RAM / 50 GB disk" is an unevidenced
  recommendation, not a qualified envelope.
- **Residual operations.** M2.5 delete retention (BFF/CP rows, VM dir, volume
  row, backing file persist); JWT/encryption key coupling (#336); the audit
  crash window (#706); and distinct `metrics_bind` values are required when
  running more than one stord per host.
  #711 (detached-open session) is exercised by the rc.2 lane's F7 sweep
  (base VM created before an agent restart, deleted after; 0 sessions left).
  #709 (first-enrollment bootstrap audit gap) is asserted by the rc.2 lane's
  deploy leg (`node_bootstrap_results.success = 1` on the issued identity).
  Sessions orphaned by a crash on a **pre-upgrade** stord (the old detach left
  `runtime_status = "open"`) are not reclaimed by the VM-delete sweep, because
  they are indistinguishable from a live opened-but-attach-pending session;
  `DeleteVolume` closes every session with no attached VM before destroying,
  so these orphans clear on volume destroy. A session still attached to a VM
  keeps the destroy refusal; if a failed drain left a dead VM's id on the row,
  detach that volume from the named VM before attempting the delete — a failed
  delete attempt tombstones the volume `'Deleting'`, which refuses the detach
  and replays the failure on retry. The detach mutation honors an explicit
  `vm_id`, so it can name the dead VM after the control plane cleared the
  attachment.
- **UI evidence scope.** The UI was not re-qualified end-to-end in prompt-04;
  scenario evidence is chvctl/BFF/API-driven (with the network-policy path
  driven through the BFF in the 2026-11-04 lane).
- **Volvisor is design-only.** ADR-028 selects it as the future storage
  authority; runtime integration is pending. The qualified path remains
  `chv-stord`.

## 4. Upgrade notes

- Back up the control-plane SQLite database before upgrading; migrations are
  forward-only and **downgrade is unsupported**. The manual rollback procedure
  is in [`package-contract.md`](package-contract.md).
- Package conffiles are `config|noreplace`; services are **not** restarted
  automatically on upgrade. Restart the units explicitly and confirm the
  four services are healthy.
- Verify the node row reports the new version after the upgrade and the agent
  reports the new version. The rc.2 fix makes that label follow the agent's
  own report; if it still lags, record it as an operational defect rather
  than assuming the upgrade failed.
- Run more than one stord per host only with distinct `metrics_bind` values;
  the default `127.0.0.1:9101` is not multi-instance-safe.
- Re-save networks after upgrade if they carry pre-#365 NULL gateways or
  pre-#369 dialect rules; pre-#481 imported/template volumes remain
  ownerless/admin-only.
- Migration operators must pass `--pause-first` (`chvctl`) or use the WebUI's
  mandatory pause-first control; the live path is rejected by design.
