## Maturity tiers

The labels are the vocabulary defined in
[`docs/DEPLOYMENT-ARCHITECTURE.md`](../DEPLOYMENT-ARCHITECTURE.md) §1.2:
**[QUALIFIED — KVM-VERIFIED]**, **[CI-VERIFIED]**,
**[CONTAINER-VERIFIED]**, **[CODE-SUPPORTED, UNQUALIFIED]**,
**[DESIGN-ONLY]**, and **[UNSUPPORTED/ABSENT]**. The qualification host is a
single shared nested-KVM host; nothing here is multi-host- or field-qualified.

## What is explicitly not claimed

- Multi-host control-plane/agent operation, multi-host migration, and the
  stretched-L2 fabric.
- Concurrent-write ("live") migration without the pause-first gate.
- Ceph RBD / iSCSI storage; K8s/CNI, Docker-forwarded, or multi-bridge
  coexistence.
- Backup/restore as disaster recovery.
- Any concurrency, density, throughput, or requests-per-second figure.
- Rolling node upgrade or downgrade. A fresh-host install + package upgrade +
  uninstall demonstration exists for `v0.4.0-rc.1` as a **container** contract
  (run [42042149140](https://github.com/o3kio/chv/actions/runs/42042149140)).
  `v0.4.0-rc.2` is disclosed as defective for clean installs and is not used
  as install evidence. `v0.4.0-rc.3`'s tarball/package path is fixed, but its
  quick installer is defective. `v0.4.0-rc.4`'s tarball/package path passed
  its lane, but its quick installer is defective (no enrolled node on a fresh
  install; a documented re-run destroys the enrolled identity), fixed in
  rc.5. The rc.5 lane runs after publication and is recorded in the living
  docs. None of this is bare-metal or cloud-VM evidence.
- Volvisor-backed storage orchestration.
- Bare-metal KVM behavior (all qualification ran nested) and host-reboot
  recovery (the cold-restart leg is the labeled subset).

## Residual boundaries that survive this matrix

These are disclosed, not hidden: the new-install data-loss defect in
`v0.4.0-rc.1`/`v0.4.0-rc.2`/`v0.3.0` (fixed in `scripts/install.sh` for rc.3,
#722) and in the `v0.4.0-rc.3` **quick installer** (fixed in rc.4, #725; see
the [rc.4 release notes](v0.4.0-rc.4-release-notes.md) §2), the VMM/serial
containment boundary (#345/#409 at v53.0), M2.5 delete retention,
JWT/encryption-key coupling (#336), the #582 multi-volume convergence-skew
residual, the #706 audit crash window (a mutation can commit before its audit
row is written; mTLS interceptor denials write no audit row), and the
requirement to set distinct `metrics_bind` values when running more than one
stord per host. Upgrading to rc.4 fixes the #722/#725 data-loss paths and
the running process's durability, but **not** the rc.4 quick-installer
enrollment/re-run defects; install rc.5 for those. Neither upgrade can
restore writes already lost.
The detached-open session (#711) and first-enrollment bootstrap audit gap
(#709) were residuals of the real-KVM-qualified candidate `e82d49a1`. Both
fixes are in the rc.2 build; the rc.2 lane exercises #711 (F7 deletes a base
VM created before an agent restart and asserts zero live stord sessions) and
asserts #709 (the deploy leg reads `node_bootstrap_results.success = 1` on
the issued identity). The residual wording below is retained only for
pre-upgrade stord data, which the fix cannot retroactively rewrite. Sessions
orphaned by a crash on a pre-upgrade stord (old detach left
`runtime_status = "open"`) are not reclaimed by the VM-delete sweep, because
they cannot be distinguished from a live opened-but-attach-pending session;
`DeleteVolume` closes every session with no attached VM before destroying, so
these orphans clear on volume destroy. A session still attached to a VM keeps
the destroy refusal; if a failed drain left a dead VM's id on the row, detach
that volume from the named VM before attempting the delete — a failed delete
attempt tombstones the volume `'Deleting'`, which refuses the detach and
replays the failure on retry. The detach mutation honors an explicit `vm_id`,
so it can name the dead VM after the control plane cleared the attachment. The
full list is in
[`DEPLOYMENT-ARCHITECTURE.md` §9](../DEPLOYMENT-ARCHITECTURE.md#9-known-boundaries-and-residual-risk).
