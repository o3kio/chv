## 1. This is a release candidate, not stable

This build is for evaluation and staged rollout with an operator who has read
the support matrix and the known limitations. It does **not** claim multi-host
operation, HA/control-plane failover, live (concurrent-write) migration,
backup/restore as DR, Ceph/iSCSI storage, Volvisor-backed storage, RPM
behavior on a real host, arm64, or any scale figure.

No field deployment has happened yet. The field-qualification campaign
([plan](../plans/2026-11-05-v0.4.0-field-qualification.md),
[profile](../DEPLOYMENT-ARCHITECTURE.md) §5 UC-11) starts from a clean rc.6
install and runs for 21–30 days; rc.5 was superseded before its window
opened. A passing field campaign is an input to the stable decision, not a
pre-approval.

## 2. Why rc.5 exists: the rc.4 quick installer did not enroll

`v0.4.0-rc.4` fixed the #722/#725 data-loss defect in the quick installer,
but its post-publication fresh-host lane
([42148690329](https://github.com/o3kio/chv/actions/runs/42148690329))
failed the quick leg with `FAIL node enrolled and visible (timeout)`. The
tarball, package, and upgrade legs passed. rc.4 is therefore defective on the
documented quick-install path and is not the final RC.

Two defects were found and fixed in [#727](https://github.com/o3kio/chv/pull/727).

### 2.1 Fresh install: no enrolled node (rc.4 regression)

`seed_admin_user` performs its direct SQLite writes with the control plane
stopped (`chv_sqlite_offline`, the #722/#725 fix). `start_services` started
`chv-agent` **before** that, so the stop landed inside the agent's enrollment
window. The agent makes exactly one enrollment attempt at startup and never
retries (`cmd/chv-agent/src/main.rs`). The RPC failed with a transport error;
the agent kept its pre-enrollment certificate (`CN=chv-agent`) plus the
configured UUID `node_id`, and every later `PublishEvent` /
`IngestNodeMetricBatch` was rejected:

```
peer node_id mismatch: rejecting impersonation attempt
  peer_node_id=chv-agent requested_node_id=<uuid>
```

`quick-install.sh` returned `rc=0` and the WebUI worked, but the node never
appeared. This is the defect the rc.4 lane caught.

**Reproduction on published rc.4 assets.** On a clean Ubuntu noble nspawn
guest, `scripts/quick-install.sh --version 0.4.0-rc.4` returned `rc=0`; the
log said `The local agent did not enroll within 90s`; the `nodes` table had
zero rows; the agent cache had `enrollment_complete: false`; the control-plane
journal repeated the peer-node-id rejection above; there were no deleted WAL
fds (the #725 durability fix held).

**The fix (#727).** `start_services` starts only `chv-stord`/`chv-nwd`; a new
`start_agent` runs **after** `seed_admin_user` on a fresh install (or
immediately on a re-run). The race is removed, not narrowed by a sleep.

### 2.2 Documented re-run/upgrade: destroyed enrolled identity

The advertised upgrade path is "re-run this script". A re-run deleted
`agent-cache.json`, re-staged the pre-enrollment certificate, and left the
already-consumed one-time bootstrap token in place. The agent then booted
with `enrollment_complete=false`, could not re-enroll with the dead token,
and kept `CN=chv-agent` plus the configured `node_id` — the same
impersonation-rejection signature. Because the old node row still had
`enrolled_at`, `wait_for_enrollment` printed **"Local agent enrolled."** and
the installer reported success anyway.

Re-running could also delete the stord/nwd sockets: the agent unit's
`RuntimeDirectory=chv` removes `/run/chv` when the agent stops, which also
holds `/run/chv/stord/api.sock` and `/run/chv/nwd/api.sock`. Certs staged
before the restart were wiped with the directory, and an agent that started
before the external daemons were listening spawned duplicates that collided
on the metrics ports.

**The fix (#727).** On a re-run, `start_services` preserves a usable enrolled
identity (cache `enrollment_complete=true` plus its durable cert/key/CA
present). Only a missing or incomplete identity clears the cache, mints a
fresh bootstrap token, and seeds it. `start_agent` stops the agent first,
restarts stord/nwd afterwards, waits for both sockets, then stages the certs
and starts the agent.

### 2.3 Local verification (rc.4 assets, clean Ubuntu noble guests)

- **Fresh install:** `rc=0`; `Local agent enrolled.`; one `nodes` row with
  `enrolled_at`; cache `true`; no deleted WAL fds; admin rotation `200` and
  login `200` after a control-plane restart.
- **Healthy re-run:** identity preserved, same `node_id`; four units active
  with `NRestarts=0`; 0 peer mismatches; the agent logged
  `external chv-stord daemon is already listening ... skipping sub-process
  spawn` (same for nwd), so no duplicate daemons.
- **Unusable-cache recovery:** the installer detected the stale identity,
  logged `no usable enrolled agent identity; re-enrolling`, seeded a fresh
  token, and re-enrolled (`enrollment_complete=true`, node row updated, 0
  peer mismatches).

## 3. What changed since v0.4.0-rc.4

### Product

- **Quick installer only (#727).** The two write-path/ordering fixes in §2.
  `scripts/quick-install.sh` is fetched from the repository at the tag; it is
  not part of the release tarball or the `.deb`/`.rpm` payloads. No Rust
  crate, migration, unit file, or package payload changed.

### Qualification (not product behavior)

- **Invariants (#727).** The qualification suite pins the fresh-install
  ordering, re-run identity preservation, cert staging after the agent stop,
  the stord/nwd socket wait, and stop-before-restart ordering. Each pin fails
  when its regression is reintroduced (verified). The suite is **174 ok /
  0 fail**; `bash -n` and `shellcheck -S warning` are clean.

## 4. If you already run an earlier release

- **`v0.4.0-rc.4` and earlier quick installs:** the quick installer can
  complete with no enrolled node (rc.4) or destroy the enrolled identity on a
  re-run (rc.1–rc.4). Do not use those quick installers for a new install or
  an upgrade.
- **`v0.4.0-rc.2` and earlier tarball/package installs:** the install path
  could lose API writes from the install process lifetime. Verify accounts
  and configuration after upgrading.
- The tarball/package path for rc.4 is unaffected by §2 and passed its lane;
  rc.5 keeps it.
- If a quick-install node never enrolled, install rc.5 and re-run it (or use
  the tarball/package path). If a re-run cleared the cached identity, rc.5
  mints a fresh token and re-enrolls.
- The seeded bootstrap password in `/etc/chv/initial_admin_password` remains
  the recovery path if a rotation was lost; the first-login rotation is
  re-prompted when `must_change_password=1`.
- Upgrading fixes the installers and the running process's durability. It
  cannot restore writes that were already lost.

## 5. Known limitations

The authoritative list is the
[support matrix](v0.4.0-rc.5-support-matrix.md) and
[`DEPLOYMENT-ARCHITECTURE.md` §9](../DEPLOYMENT-ARCHITECTURE.md#9-known-boundaries-and-residual-risk).

- **Single host only.** Multi-host control-plane/agent dispatch is
  architecturally absent; ADR-029 is accepted but not implemented. The
  VXLAN/WireGuard fabric is design-only.
- **VMM/serial containment.** Cloud Hypervisor is pinned to v53.0. The silent
  serial-manager thread death and the adopted-VM stop wedge are contained,
  not cured; re-verify at every VMM upgrade (#345 root / #409).
- **Migration is stop-the-world only.** Pause-first is required; live
  concurrent-write migration is not claimed. The underlying stord primitive
  assumes a quiescent source. One multi-volume convergence-skew residual is
  disclosed (#582).
- **Backup/restore is hard-fenced.** All backup/restore routes return
  `501 NOT_IMPLEMENTED`; there is no DR claim or restore validation.
- **Storage.** Local file and LVM are qualified; Ceph RBD and iSCSI are coded
  but unqualified. K8s/CNI, Docker-forwarded, and multi-bridge coexistence are
  not claimed.
- **Upgrade.** Package upgrade is CI-verified; rolling node upgrade is absent
  and downgrade is unsupported. The fresh-host install → operate → package
  upgrade → uninstall path (#666) and the published quick installer (#556)
  passed on `v0.4.0-rc.1` in a clean container (run
  [42042149140](https://github.com/o3kio/chv/actions/runs/42042149140)).
  rc.3's lane was green on the fixed tarball/package path but exercised a
  defective quick installer; rc.4's lane passed tarball/packages/upgrade and
  failed only the quick leg. The rc.5 post-publication lane
  ([42159563210](https://github.com/o3kio/chv/actions/runs/42159563210))
  passed all four legs, including the published quick installer in candidate
  mode (node enrolled, credential persistence across a restart, WAL
  retained); see the
  [rc.5 evidence report](../evidence/production-readiness/v0.4.0-rc5/fresh-host-qualification.md).
  The lane installs once, so the documented re-run path still rests on the
  local clean-guest verification in #727. None of this is bare-metal or
  cloud-VM evidence.
- **Scale.** No concurrency, density, throughput, or requests-per-second
  claim. M4.8 numbers are single-host baselines.
- **Hardware minimums.** "4 cores / 8 GB RAM / 50 GB disk" is an unevidenced
  recommendation, not a qualified envelope.
- **Residual operations.** M2.5 delete retention (BFF/CP rows, VM dir, volume
  row, backing file persist); JWT/encryption key coupling (#336); the audit
  crash window (#706); and distinct `metrics_bind` values are required when
  running more than one stord per host.
  #711 (detached-open session) is exercised by the rc.2 lane's F7 sweep.
  #709 (first-enrollment bootstrap audit gap) is asserted by the rc.2 lane's
  deploy leg. Sessions orphaned by a crash on a **pre-upgrade** stord are not
  reclaimed by the VM-delete sweep; `DeleteVolume` closes every session with
  no attached VM before destroying, so these orphans clear on volume destroy.
  The full wording is in §9 of the architecture document.
- **UI evidence scope.** The UI was not re-qualified end-to-end in prompt-04;
  scenario evidence is chvctl/BFF/API-driven.
- **Volvisor is design-only.** ADR-028 selects it as the future storage
  authority; runtime integration is pending. The qualified path remains
  `chv-stord`.

## 6. Upgrade notes

- Back up the control-plane SQLite database before upgrading; migrations are
  forward-only and **downgrade is unsupported**. The manual rollback procedure
  is in [`package-contract.md`](package-contract.md).
- Package conffiles are `config|noreplace`; services are **not** restarted
  automatically on upgrade. Restart the units explicitly and confirm the
  four services are healthy.
- Verify the node row reports the new version after the upgrade and the agent
  reports the new version. If it still lags, record it as an operational
  defect rather than assuming the upgrade failed.
- Run more than one stord per host only with distinct `metrics_bind` values;
  the default `127.0.0.1:9101` is not multi-instance-safe.
- Re-save networks after upgrade if they carry pre-#365 NULL gateways or
  pre-#369 dialect rules; pre-#481 imported/template volumes remain
  ownerless/admin-only.
- Migration operators must pass `--pause-first` (`chvctl`) or use the WebUI's
  mandatory pause-first control; the live path is rejected by design.
- **Quick-install users on rc.1–rc.4:** install rc.5 and re-run it (or upgrade
  through the packages), then verify the admin password, users,
  configuration, and that the node appears in `/v1/nodes`.
