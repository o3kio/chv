## Amendment 2026-11-06 — rc.2 superseded by rc.3

`v0.4.0-rc.2` was published, but its post-publication fresh-host lane found a
**blocker-class clean-install data-loss defect**: the installer's direct
`sqlite3` writes unlinked the WAL the live control plane still held open, so
API writes acknowledged after install (the documented first-login password
rotation, created users, configuration and audit rows) were lost on the next
restart or upgrade. The defect exists in `v0.3.0`, `v0.4.0-rc.1`, and
`v0.4.0-rc.2`; `v0.4.0-rc.3` fixes it (#722).

Consequences for this plan:

- Stage B's artifact is **`v0.4.0-rc.3`**, not rc.2. rc.2 remains published
  and is not rewritten; it is disclosed as defective and must not be
  promoted.
- Every **forward-looking** instruction in this plan that names rc.2 as the
  artifact to qualify, the field upgrade target, the clean-window install, or
  the stable base reads **rc.3**. Statements that record what rc.2 *did*
  (including the blocker discovery and the rc.2 lane) remain historically
  accurate.
- The Stage D stable-prep delta check becomes
  `git diff --name-only v0.4.0-rc.3..HEAD`; it and the stable tag must contain
  the rc.3 product code (which is the rc.2 runtime plus the installer fix).
- The field upgrade drill is `v0.4.0-rc.1 → v0.4.0-rc.3` **or**
  `v0.3.0 → v0.4.0-rc.3`, with one control-plane restart of the old release
  before any identifiable-state writes (the old installers have the defect).
  The window itself starts from a clean rc.3 install.

- **B1 (blocker).** The packaged agent unit's closed device cgroup allowed
  `/dev/kvm` but not `/dev/net/tun`. Cloud Hypervisor could not attach a
  virtio-net device, so every boot failed and the VM had no NIC.
- **B2 (blocker).** `start_vm` recorded `succeeded` on a non-2xx `vm.boot`
  (four `status=500` in six successful operations); the VMM stayed `Created`
  while the BFF showed the desired `Running` state.

  installer-created `chvbr0` and the nwd default-network bridge both owned

  guest's gateway ARP stayed `FAILED`.
- **B4 (blocker for the documented network profile).** dnsmasq had no
  writable lease file; its compiled default is outside nwd's
  `ProtectSystem=strict` roots, so it exited `Permission denied` and DHCP

  release-directory/tarball mode printed and recorded `Version: 0.3.0` while

## Amendment 2026-11-06 — rc.7 disqualified by its own pre-window drill; rc.8 is the final RC

The **published** `v0.4.0-rc.7` artifact was installed on `field-host-1` as
the documented package upgrade over the rc.6 tarball install. Configuration,
database rows, certificates, the node identity, and the running VM survived
the upgrade, but two blocker-class defects reproduced:

- **B8 (blocker for the documented network profile).** `chv-nwd` runs as
  non-root `chv` with only `CAP_NET_ADMIN CAP_NET_RAW CAP_SYS_ADMIN`.
  dnsmasq must bind UDP/67 and the host's
  `net.ipv4.ip_unprivileged_port_start` is 1024, so every spawn exited
  `dnsmasq: failed to bind DHCP server socket: Permission denied`. Re-running
  the same spawn with `CAP_NET_BIND_SERVICE` added binds exclusively to the
  bridge.
- **B9 (blocker; failed documented recovery under §6.4/§6.9).** The
  `TopologyTable` is in-memory only. After the documented
  `systemctl restart chv-nwd` (PID `133166` → `174335`), a policy update
  stayed `RetryPending` through the dispatch-retry budget and failed
  `DISPATCH_FAILED` with
  `set_firewall_policy failed: not found: topology eac319350ba9fff7b0b957aedef20ba6 (NOT_FOUND)`,
  even though the bridge, TAPs, and nft table still existed. `core-managed`
  reconcile is observe-only (`require_mutation()` returns early), so nothing
  re-ensures the network and the defect does not self-heal.

Two operational follow-ups found while reviewing the B9 fix are also in rc.8:
DHCP MAC→IP reservations lived under `/run/chv/nwd`, which
`RuntimeDirectory=` wipes on every restart; and a topology journal or
reservation set from a deleted deployment survived `--wipe` and package
removal.

The full evidence is
[`01-rc6-blockers.md`](../evidence/production-readiness/v0.4.0/field-qualification/01-rc6-blockers.md)
Part 2, with raw artifacts under
[`artifacts/05-rc7-prewindow-drills/`](../evidence/production-readiness/v0.4.0/field-qualification/artifacts/05-rc7-prewindow-drills/).
`v0.4.0-rc.7` cannot open the field window or be the stable base.

Consequences for this plan:

- Stage B's artifact is **`v0.4.0-rc.8`**. rc.7 remains published and is not
  rewritten; it is disclosed as defective. Its tag, assets, and lane claims
  are historical.
- Every **forward-looking** instruction that names rc.7 as the artifact to
  qualify, the field upgrade target, the clean-window install, or the stable
  base reads **rc.8**. Statements that record what rc.7 *did* (including this
  pre-window upgrade/restart drill) remain historically accurate.
- **rc.8 changes product code** (the nwd unit capabilities, the nwd
  topology/journal and DHCP state paths, the agent startup path, and the
  installer/package cleanup paths). The rc.2 real-KVM lane and the rc.7
  pre-window drill do not cover that delta. rc.8 is covered by targeted Rust
  tests, packaging/architecture contract tests, a pre-window drill of its own
  after publication, and nothing more until those runs exist.
- The Stage D stable-prep delta check becomes
  `git diff --name-only v0.4.0-rc.8..HEAD`; it and the stable tag must contain
  the rc.8 product code, with only `docs/` and `CHANGELOG.md` allowed after
  the final RC.
- **Upgrade order is part of the contract.** `rc.7 → rc.8` requires
  `chv-nwd` to be restarted before or with `chv-agent`, so the agent's
  startup replay reaches rc.8 nwd and seeds the journal.
  `chv-agent.service` already orders `After=chv-nwd.service`; a combined
  `systemctl restart chv-nwd chv-agent` is correct. The package scripts
  deliberately do not restart services.
- **Replay semantics are deliberate.** The agent replays only networks nwd
  does not already own. nwd recovers its journal before serving, and a VM
  definition is a create-time snapshot, so replaying an already-owned network
  could roll a later CIDR/gateway change back. A failed ownership query falls
  back to replaying everything (the upgrade case).
- **Policy recovery is part of the contract.** §6.4 requires policy *and*
  bridge to re-materialize. The last requested firewall/NAT policy and
  version are journaled under `/var/lib/chv/nwd/policies` and re-applied
  fail-closed before serving, because nftables survives a process restart but
  not a host reboot and the in-memory record re-scopes the guard on attach.
  A recovered topology without its guard would leave new taps outside CHV
  default-deny (the base hooks are `policy accept`). Unapplicable payloads
  are rejected before journaling (recovery is fail-closed, so a poison entry
  would crash-loop nwd), and a persisted entry that still cannot be re-applied
  aborts startup with an error naming the exact file.
- **Fabric topologies are not journaled.** The stretched-L2 fabric is
  design-only and its provider owns its durable surface. Bridge-only
  topologies are the supported profile; an nwd restart is not claimed to
  rebuild a fabric overlay.
- **One-time reservation gap.** Reservations written by rc.7 under
  `/run/chv/nwd` are not migrated. The upgrade restart re-creates the
  topology but not the per-NIC reservations; a DHCP guest keeps its current
  lease until renewal, and a VM re-create or a clean rc.8 install repopulates
  the persistent file. The upgrade leg uses cloud-init static addressing; the
  reservation-survives-restart contract is exercised on the clean install.
- **One-time policy-journal gap.** The rc.7 → rc.8 upgrade also starts with
  an empty policy journal. The rc.7 nft guard persists in the kernel, so the
  running guests stay filtered; the journal is seeded by the first
  attach-time policy application (the core runtime applies the NIC snapshot
  or the DP4 baseline before every attach) or by the operator's first policy
  update. The upgrade drill performs that policy update immediately after the
  restart and verifies the guard re-scopes. No rc.8 clean-install path has
  this gap: the network's policy is applied before serving and journaled on
  the same call.
- The rc.7 pre-window work on `field-host-1` is **rc.7 evidence**. It cannot
  qualify rc.8. After rc.8 is published, repeat on `field-host-1`: the
  upgrade drill (`rc.7 → rc.8` or `v0.3.0 → rc.8`) restarting nwd before/with
  the agent, uninstall/purge, a clean rc.8 tarball install, a documented
  start with a guest DHCP lease and a `login:` console, a policy change plus
  nwd restart with the reservation surviving, and two consecutive `--wipe`
  installs reaching `TenantReady`. Only then does the 21–30 day window start.
- Do not tag stable on rc.7: its default DHCP path cannot bind the server
  socket and an nwd restart loses the topology table.

## 1. Purpose

Take the published release candidate through one bounded, reproducible field
deployment, then decide whether the **exact tested commit** is ready for a
stable `v0.4.0` tag.

The objective is not to demonstrate every repository feature. It is to prove
one coherent single-host product profile that an operator could realistically
adopt, and to keep the published support matrix narrower than or equal to the
evidence.

This plan deliberately does **not** start multi-host dispatch (MH-A) or
Volvisor. [ADR-029](../specs/adr/029-multi-host-dispatch.md) is accepted but
not implemented: the control plane reaches an agent only through a local
filesystem path, and the agent has no TCP gRPC listener. A multi-node field
profile would therefore be theatre, not evidence. The transition plan's Phase
P1 starts only after the stable gate in §7 is met.

### 2.1 Truth defect fixed in rc.2: node-row version lag

At the time of writing, the API/WebUI node row reports
`nodes.agent_version` (`crates/chv-webui-bff/src/handlers/nodes.rs:64`), while
that column was refreshed only by the enrollment upsert
(`crates/chv-controlplane-store/src/nodes.rs`, `agent_version =
EXCLUDED.agent_version`). Periodic inventory deliberately sends
`chv_agent_version: None` and the upsert preserves the old value, so reading
`node_inventory.chv_agent_version` instead would not have fixed the lag. An
in-place package upgrade could therefore leave the node row showing the
previous release while every binary reported the new one — the lag recorded
in the fresh-host report §6.

This affects the field campaign's upgrade-skew question, so it is fixed in
`v0.4.0-rc.2`: the agent's periodic `ReportServiceVersions` report now
refreshes `nodes.agent_version` (no-op when unchanged), with a regression
test that reports `rc.2` over a node seeded at `rc.1` and reads the result
back through `POST /v1/nodes` (PR #720). The sibling
`node_inventory.chv_*_version` columns stay enrollment-time values; they have
no readers, and the code records that boundary. The field upgrade drill
still verifies the label on the real host.

### Stage B — `v0.4.0-rc.2` (historical)

> Superseded by the rc.3/rc.4/rc.5/rc.6/rc.7 amendments above. This section records how
> rc.2 was cut; it is not the current release instruction.

Scope is deliberately small: the version-truth fix, any Stage A correctness

Release mechanics:

  stable tag is pushed, and a 21–30 day early date would be wrong. The
  `[0.4.0]` section is written on tag day in the docs-only stable-prep commit
  (Stage D, decision D4). If field qualification needs a product fix, cut
  rc.3; never tag stable on code that was not tested.
- `scripts/install.sh` keeps `fallback_version="0.3.0"` during the RC window.
  v0.4.0 does not exist yet; the flip is a post-stable action (Stage D).
- The release notes and support matrix are written as
  `docs/release/v0.4.0-rc.2-release-notes.md` and
  `docs/release/v0.4.0-rc.2-support-matrix.md`; they state that rc.2 is a
  **pre-release** and name the exact evidence delta from rc.1.

Verification before the tag is considered published:

- full local gate: `cargo fmt --all -- --check`, clippy with `-D warnings`,
  nextest workspace, doctests;
- required CI checks on the merge commit, including the 30-minute E2E budget
  set by #717;
- signed annotated tag, verified locally (`git tag -v`) and on GitHub;
- published asset set checked with `sha256sum -c --strict SHA256SUMS`, exactly
  four `.deb` and four `.rpm` dot-named packages, no tilde names, no
  `0.0.1` placeholder, prerelease flag set;
- post-publication fresh-host lane on the rc.2 tag with

- pinned quick-install dry run resolves the published rc.2 artifacts.

([42120903098](https://github.com/o3kio/chv/actions/runs/42120903098)).

Preconditions, all of which must be true before the host is touched:

- the reference profile (canonical text: [DEPLOYMENT-ARCHITECTURE.md](../DEPLOYMENT-ARCHITECTURE.md)
  §5 UC-11) is approved and merged;

### Stage D — stable `v0.4.0`

The stable tag carries the exact rc.7 **product code**. The only permitted
delta is a docs/evidence-only stable-prep commit that records the field
decision and the correct changelog date. This is decision D4, disclosed in the
release notes; it is not a silent exception.

1. Branch from the exact `v0.4.0-rc.7` tag and create the stable-prep commit:
   - `CHANGELOG.md` `[0.4.0]`, dated **tag day**, with the same change set as
     rc.7 and no product changes;
   - the filled field report and support decision;
   - `docs/release/v0.4.0-support-matrix.md` and
     `docs/release/v0.4.0-release-notes.md`, with the profile's exclusions;
   - the UC-11 status flip (planned → field-qualified) and the §7
     qualification-status row, both pointing at the filled field report, only
     when the report is filled and linked.
2. Prove the delta is docs/evidence only: `git diff --name-only
   v0.4.0-rc.7..HEAD` must list only paths under `docs/` plus
   `CHANGELOG.md`. Any other path means stop and cut a new RC — do not tag
   stable.
3. Tag the stable-prep commit as `v0.4.0` with a signed annotated tag; verify
   it locally and on GitHub.
4. The workflow validates `[0.4.0]`, builds from the tag, publishes as a
   **non-prerelease**, and produces the expected asset/checksum contract with
   stable names. Because the product code is identical to rc.7, the binaries
   are built from the same source; the release notes say so.
5. Verify `releases/latest` resolves `v0.4.0`, the tarball sidecar verifies,
   the package set matches `SHA256SUMS`, and internal package versions are
   `0.4.0` (no `~rc` suffix).
6. After publication, merge the stable-prep docs back to `main` (docs-only),
   flip `fallback_version` to `0.4.0`, replace "v0.3.0 latest stable" in
   `DEPLOYMENT.md`, `install/from-github-release.md`, and the README, and run
   the **unpinned** quick installer for the first time.

**Why not tag the exact rc.7 commit?** That would need a `[0.4.0]` section at
rc.7, dated 21–30 days before the tag, which violates the versioning policy's
date rule; the other option is `skip_changelog_check`, which weakens the
release gate. The docs-only stable-prep commit keeps the date truthful and
puts the field evidence in the stable tree. It is a recorded exception to the
literal "no new commits" sentence in
[release-process.md](../release/release-process.md); the product code is
unchanged and the delta is machine-checked in step 2. The strict alternative
(tag rc.7 and merge evidence after) is recorded in D4; it avoids the exception
but leaves the tag without the field report.

Only after stable and the field decision exist:

1. Start transition-plan P1 (remote dispatch/transport/PKI) per ADR-029.

3. Keep Volvisor deferred until MH-A transport and field evidence exist and

## 5. Reference profile

The canonical profile is recorded in
[DEPLOYMENT-ARCHITECTURE.md](../DEPLOYMENT-ARCHITECTURE.md) §5 UC-11.
In summary:

| Dimension | Profile |
|---|---|
| Topology | **One host** running control plane, agent, stord, nwd, and nginx; internal listeners loopback; nginx is the edge |
| Host | Ubuntu 24.04 noble, amd64; **bare metal preferred**. A KVM-capable cloud VM is allowed only when it exposes `/dev/kvm`, and it is recorded as virtualized — never described as bare metal. Hardware is recorded, not promoted to a minimum |
| VMM | Cloud Hypervisor **v53.0**, digest-verified by the installer |
| Artifacts | Published **`.deb`** set and tarball for `v0.4.0-rc.7`. The field host's clean install uses the published tarball's `scripts/install.sh` (release-directory mode) because the `get.cellhv.com` hosting surface is not stood up; the pinned quick installer remains a supported container-verified path but is not used for this window. The upgrade drill starts from the published rc.1, rc.5, rc.6, or v0.3.0 artifacts and moves to rc.7 packages. RPM excluded |
| Storage | Local directory + **LVM**; no iSCSI/Ceph/Volvisor |
| Network | Default single-host bridge only; no VLAN, no fabric/VXLAN |
| Lifecycle | Core-managed authority; **stop-first**, not pause-first |
| Workload | 3–5 VMs; repeated create/delete; start/stop/reboot; console; one policy change; LVM attach/use |
| Upgrade | `v0.4.0-rc.1` → `v0.4.0-rc.7`, `v0.4.0-rc.5` → `v0.4.0-rc.7`, `v0.4.0-rc.6` → `v0.4.0-rc.7`, or `v0.3.0` → `v0.4.0-rc.7` package upgrade on the field host **before the window opens**; restart the old release's control plane once before any identifiable-state writes (the old installers carry the WAL-unlink defect); the window itself runs on a clean rc.7 install |
| Data | **Disposable qualification data only** — no backup means no data-protection claim |
| Duration | 21 days minimum, 30 preferred |

**Why one host.** The CP→agent dispatch surface is a local Unix-socket path and
the agent has no TCP gRPC listener; remote nodes cannot be enrolled or driven.
The Prompt 06 example of one control plane plus two or three compute nodes is
therefore not a coherent profile for this release. Narrowing the topology is
the honest choice; a multi-node deployment would not exercise a supported
product path.

**What this profile does not claim:** multi-host, HA, control-plane failover,
migration (the M4.6 quiescent two-stord primitive is not a product migration
feature), backup/restore (hard-fenced `501`), scale/density/throughput,
RPM, arm64, hardware minimums, S3/object-storage credentials, or Volvisor.

## 6. Field campaign execution

### 6.1 Pre-flight (before the window starts)

Record and commit to the evidence directory:

- host identity (redacted), CPU model/flags, `/dev/kvm` presence, memory,
  disk layout, kernel, firmware, Cloud Hypervisor build, OS image digest;
- CHV package versions and their checksums; the exact rc.7 tag and release
  asset digests;
- network topology and the edge/TLS configuration (redacted);
- storage layout and the exact volume classes used;
- baseline resource snapshot: daemon RSS/CPU, DB size, open fds/sockets, CHV
  processes, taps/veth/bridges/netns, nftables object counts, stord session
  and volume rows.

Rehearse the upgrade path in the reference topology: install rc.1 (or
v0.3.0) from the published artifacts (tarball/`install.sh`), restart the old
release's control plane once before any identifiable-state writes (the old
installers unlink the WAL the running control plane holds, so acknowledged
writes otherwise vanish at the first restart), perform the identifiable
writes (for example the first-login password change), run a VM, upgrade the
packages to rc.7, restart the services per the documented procedure, verify
config, DB, certificates, the operator account, VM survival, and the node's
reported version (the node row reports the base `0.4.0`; the rc.7 artifact is
discriminated by the package version `0.4.0~rc.7` and the commit banner
printed by the binaries). When the source host is rc.6 or older, also remove
the legacy `chvbr0` and its persisted config manually (a plain installer
re-run refuses while persistent data exists) and record the before/after
owner set of `10.200.0.1`; a package upgrade does not edit host network
configuration.
Then uninstall/purge and perform a clean rc.7 install. The clean rc.7
install is the one the field window starts from, so the window proves
reproducibility from published artifacts and docs.

### 6.2 Deployment from released artifacts

Use only the published rc.7 packages/tarball and the documented install path.
No source builds, no local patches, no `cargo run`, no unreleased images. If a
documented step is wrong or missing, that is an operational defect: record it,
fix the doc in a follow-up, and repeat the clean install rather than
improvising silently.

### 6.3 Normal workload

Run a bounded workload long enough to observe steady state:

- 3–5 VMs, repeatedly created and deleted across the window;
- start/stop/reboot cycles, including a VM left running across daemon
  restarts;
- serial console and normal operator visibility (UI, CLI, API);
- one live network-policy change with a before/after connectivity check;
- LVM-backed volume attach/use/detach, including a delete that closes the
  session.

Do not invent a mid-window upgrade: the campaign runs on rc.7, so there is no
successor unless a blocker forces a new RC. The rc.1 → rc.7 (or v0.3.0 → rc.7)
drill is executed in the reference topology before the window (and repeated if
a successor RC appears).

### 6.4 Planned failure and recovery drills

Each drill records the contract, the observed behavior, the recovery time, and
whether any residue remained. Run each at least once; repeat the destructive
ones only after the deployment is healthy again.

| Drill | What must hold |
|---|---|
| Control-plane restart | CP returns; running VMs unaffected; mutations resume; no duplicate operation effects |
| Control-plane outage (kill, observe, restore) | Published partition policy holds; running VMs continue; queued mutations fail or replay per contract; no split authority |
| Agent restart with running VMs | VMs survive; desired state converges; no detached-open stord sessions (#711) |
| stord restart during/after an operation | Sessions reconcile; failed operations are visible with a safe next action; no silent `Active` |
| nwd restart / network disruption | Policy and bridge re-materialize; no unintended guest connectivity gap; no orphan taps/nft |
| **Real host reboot** with running VMs | Units return; VM state and data are preserved; the documented recovery action brings VMs back (auto-start or an explicit start); no orphan processes/taps/netns/nft |
| Certificate/enrollment failure (safe reproduction) | Fails closed with a clear diagnostic; documented recovery works; first enrollment's `ReportBootstrapResult` is accepted, not rejected by the peer-node-id check (#709) |
| Upgrade rc.1, rc.5, rc.6, or v0.3.0 → rc.7 before the window opens, on the field host | Install rc.1 (or rc.5/rc.6/v0.3.0), restart its control plane once before any identifiable-state writes (the old installers carry the WAL-unlink defect), perform the identifiable writes, run a VM, upgrade packages to rc.7, restart per the documented procedure: config, DB, certs, operator account, and the VM survive; **for an rc.6/older source host, remove the legacy `chvbr0` and its persisted config manually (a plain installer re-run refuses while persistent data exists) and record the before/after `ip -o -4 addr show` owner set**; the package version is `0.4.0~rc.7` and the node row reports the base `0.4.0` (from an rc.1 start that row value is unchanged); the downgrade boundary is stated |
| Delete-after-agent-restart | VM delete closes the volume session; no orphaned `open` row (#711) |
| Failed upgrade / rollback | The documented manual rollback path is followed; no data loss; downgrade remains explicitly unsupported |

Prompt 06's migration-interruption and backup-target-outage drills are **out
of profile**: this release claims neither migration as a product feature nor
backup/restore. Record them as not run; the omission is a scoped exclusion,
not a pass.

### 6.5 Observability and operator usability

For each question, record whether the operator can answer it from supported
tools, and what was missing:

- which VMs are running, and on which node;
- node health, readiness, and **reported version**;
- failed or stuck operations and the reason;
- migration progress — out of profile for this release; record that it is not
  offered as a supported action;
- storage and network failures;
- certificate/enrollment failures;
- resource pressure;
- what action is safe next.

Missing metrics, logs, or runbook steps are operational defects, not
documentation niceties.

### 6.6 Resource and leak checks

Across the campaign, check for unexplained growth or residue in:

- daemon RSS/CPU and restart counts;
- SQLite/DB size and WAL behavior;
- open files/sockets per daemon;
- Cloud Hypervisor processes;
- TAP/veth/bridge/netns objects;
- nftables tables/chains/rules;
- stord volume/session state;
- temporary backup/migration artifacts (none should be created in this
  profile).

### 6.7 Cadence

- **Daily:** daemon/unit health, node health and version, VM states, failed
  operations, `/metrics` endpoints, disk/inode growth, orphan scan.
- **Weekly:** create/delete batch, lifecycle cycle, console check, policy
  change, LVM attach/detach, log review for errors that did not page.
- **Drill days:** schedule destructive drills early in the week so there is
  time to recover and observe steady state before the weekend.
- **End of window:** final leak scan, final rollback check (downgrade
  boundary), and the support decision.

To be produced under
`docs/evidence/production-readiness/v0.4.0/field-qualification/`:

| File | Contents |
|---|---|
| `00-profile-and-host.md` | Approved profile, host record, versions, digests |

| `03-drills.md` | One section per drill: contract, observed, recovery, residue |

### 6.9 Pass/fail classification

**Terminate the field qualification and fix before stable (blocker-class):**

- guest-to-host or guest-to-guest isolation breach;
- data corruption or loss on the qualified storage path;
- authority split or state divergence that does not self-heal;
- failure to recover after a documented restart/reboot;
- credential or key exposure;
- VM/process/volume/network residue that survives documented cleanup;
- upgrade destroys configuration, database, certificates, or the operator
  account;
- an unresolved defect that requires hidden maintainer knowledge for ordinary
  recovery.

**Acceptable only if documented with an operator workaround:**

- missing non-critical metrics or cosmetic UI defects;
- single-host SPOF (inherent and disclosed);
- no backup/HA/migration/multi-host;
- RPM untested;
- pause-first convergence skew (#582) if the profile stays stop-first;
- JWT/encryption-key coupling (#336) if the profile uses an explicit
  `CHV_ENCRYPTION_KEY` and no S3 target;
- audit crash window (#706) and dedicated stord user (#700) as disclosed
  security/operability residuals;
- M2.5 delete retention (BFF/CP rows, VM directory, volume row, and backing
  file persist after a successful delete) as a disclosed pre-existing
  residual; the truthful delete signal is the task/operation result.

Any "acceptable" item that threatens isolation, data integrity, authority, or
recovery is reclassified as blocker-class. Do not turn an unresolved
blocker-class defect into a documentation-only workaround.

### 6.10 Termination and rollback

If a blocker-class defect appears:

1. Stop new mutations; preserve logs, DB, and evidence.
2. Classify whether running workloads are safe; if not, stop them in the
   documented order.
3. Fix on a branch, cut a new RC (for example `v0.4.0-rc.8`), publish it, and
   restart the field window for the new artifact. Field evidence from the
   superseded artifact remains labelled with that artifact; it is not
   transferred to the successor.
4. Do not patch the field host in place and continue as if the published
   artifact were tested.

Downgrade is unsupported. Rollback follows the documented manual procedure
and must be rehearsed once, with data-loss boundaries recorded.

## 9. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| No durable KVM host | Blocks Stage C | Decide host source now; bare metal or KVM-capable cloud VM; never the shared CI runner |
| Field bug forces a new RC | Slips stable 2–4 weeks | Keep each RC's scope tiny; classify blockers before the window; only cut a new RC for blockers |
| No backup in profile | Data loss if misused | Disposable data only; state "not a data-protection solution" in the profile and release notes |
| Single host is a SPOF | Full outage | Disclose; no HA claim; HA remains out of scope until multi-host |
| Version-label bug ships | Misleading upgrade truth | Fixed in rc.2; assert the node version after upgrade in the field drill |
| Kernel/VMM variance | New failures | Pin noble + CHV v53.0; record kernel/firmware; treat deviation as out-of-profile |
| RPM adopted untested | Install failure | Deb-only claim; keep RPM labeled built/unexercised |
| #336/#700/#706 residuals | Security/operability debt | Explicit key, no S3, no shared multi-tenant host; disposition in §6.9/§8 |
| Signing keys unavailable | Stable unverifiable | Confirm the signing path before Stage D; do not publish unsigned stable silently |
| Docs-only stable-prep delta | Drift mistaken for a product change | Allowlist `git diff --name-only` to `docs/` + `CHANGELOG.md`; disclose the delta; cut a new RC on any other path |
| Tag-protection bypass remains | Governance risk | Remove/re-justify after the RC window |
| Bus factor (#665) | Campaign stalls | Write the field runbook so a second operator can execute it; keep org-admin items visible |
