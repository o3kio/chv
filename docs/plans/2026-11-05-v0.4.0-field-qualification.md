> **Status: Proposed — not started. No field evidence is claimed.**
> This plan sequences the work after the `v0.4.0-rc.1` publication. It does not
> move any capability tier, does not authorise a stable tag, and does not

## 1. Purpose

Take the published release candidate through one bounded, reproducible field
deployment, then decide whether the **exact tested commit** is ready for a
stable `v0.4.0` tag.

The objective is not to demonstrate every repository feature. It is to prove
one coherent single-host product profile that an operator could realistically
adopt, and to keep the published support matrix narrower than or equal to the
evidence.

This plan deliberately does **not** start multi-host dispatch (MH-A) or
Volvisor. [ADR-029](../specs/adr/029-multi-host-dispatch.md) is accepted but
not implemented: the control plane reaches an agent only through a local
filesystem path, and the agent has no TCP gRPC listener. A multi-node field
profile would therefore be theatre, not evidence. The transition plan's Phase
P1 starts only after the stable gate in §7 is met.

### 2.1 Open truth defect: node-row version lag

At the time of writing, the API/WebUI node row reports
`nodes.agent_version` (`crates/chv-webui-bff/src/handlers/nodes.rs:64`), while
that column is refreshed only by the enrollment upsert
(`crates/chv-controlplane-store/src/nodes.rs`, `agent_version =
EXCLUDED.agent_version`). Inventory reports update
`node_inventory.chv_agent_version` instead. An in-place package upgrade can
therefore leave the node row showing the previous release while every binary
reports the new one — the lag recorded in the fresh-host report §6.

This is a version-truth defect that directly affects the field campaign's
upgrade-skew question. It must be either fixed in `v0.4.0-rc.2` (preferred:
read `COALESCE(ni.chv_agent_version, n.agent_version)` or refresh
`agent_version` on inventory, plus a regression test) or explicitly disclosed
in the field support decision. It must not be silently carried into stable.

## 3. Sequencing rule and stages

Each stage ends in evidence, not a merged-PR checklist. A stage does not start
until the previous exit gate is met.

| Stage | Purpose | Entry gate | Exit gate | Estimate |
|---|---|---|---|---|
| **A** | Close RC-lineage evidence | `v0.4.0-rc.1` published; living docs truth fixed | Exact-lineage real-KVM run triaged; version-truth fix merged; rc.2 scope frozen | 2–3 days |
| **B** | Cut and publish `v0.4.0-rc.2` | Stage A exit | rc.2 published as pre-release; post-publication fresh-host + asset verification green; upgrade target exists | 3–5 days |
| **C** | Field qualification (Prompt 06) | Profile + campaign plan merged; real host provisioned; rc.2 published | Filled field report; zero blocker-class defects; support decision published | 21–30 day window + 3–5 days setup |
| **D** | Promote stable `v0.4.0` | Stage C exit | Stable tag on the exact rc.2 commit; assets verified; release page links field evidence; post-stable installer truth updated | 2–3 days |
| **E** | Hand off to MH-A | Stable published; field evidence exists | Transition-plan P1 entry criteria met | next programme |

### Stage A — close the RC-lineage evidence gap

1. Run the full real-KVM lane against the **tag ref**, never `main`:
   `gh workflow run nightly-kvm-qualification.yml --ref v0.4.0-rc.1 -f lane=full`.
   If the shared `chv-kvm` runner is offline, the run stays queued (visible,
   never green); do not substitute a container, and do not treat a queued run
   as evidence.
2. Triage every failure into: fixed for rc.2, documented limitation, or
   refused path. Do not convert an isolation/data-integrity/authority defect
   into a documentation workaround.
3. Close #709/#711 **only** if the run's scenario set actually exercises
   first-enrollment bootstrap and delete-after-agent-restart on that exact
   lineage. If a scenario does not cover the bug, add it or keep the issue
   open; a green adjacent leg is not evidence for the specific defect.
4. Merge the node-row version-truth fix with a regression test, or record why
   it is deferred and disclose it in the field decision.
5. Confirm `main` and the release tag still agree on product paths; record
   the delta between the RC tag and the fixes going into rc.2.

**Exit:** run link recorded; each failure classified; #709/#711 disposition
recorded; rc.2 content frozen to truth/correctness fixes only.

### Stage B — `v0.4.0-rc.2`

Scope is deliberately small: the version-truth fix, any Stage A correctness
fix, and the docs/release-prep changes needed to make rc.2 a coherent
successor. No features, no refactors, no multi-host work. Cut the release-prep
branch from current `main` so the #717 E2E budget and any merged docs are
included; do not retag or rewrite rc.1.

Release mechanics:

- `VERSION` stays `0.4.0`; the tag is `v0.4.0-rc.2`; the internal package
  version is `0.4.0~rc.2`; published asset names remain GitHub-safe
  (`..._0.4.0.rc.2_...`, RPM `...-0.4.0.rc.2-1...`).
- `CHANGELOG.md` gains `[0.4.0-rc.2]`. Release-prep also adds the `[0.4.0]`
  section (same change set, dated at the planned promotion date) so a stable
  tag can be placed on the rc.2 commit without a post-RC changelog commit. If
  field qualification later needs a product fix, cut rc.3 and move the
  `[0.4.0]` section there; never tag stable on code that was not tested.
- `scripts/install.sh` keeps `fallback_version="0.3.0"` during the RC window.
  v0.4.0 does not exist yet; the flip is a post-stable action (Stage D).
- The release notes and support matrix are written as
  `docs/release/v0.4.0-rc.2-release-notes.md` and
  `docs/release/v0.4.0-rc.2-support-matrix.md`; they state that rc.2 is a
  **pre-release** and name the exact evidence delta from rc.1.

Verification before the tag is considered published:

- full local gate: `cargo fmt --all -- --check`, clippy with `-D warnings`,
  nextest workspace, doctests;
- required CI checks on the merge commit, including the 30-minute E2E budget
  set by #717;
- signed annotated tag, verified locally (`git tag -v`) and on GitHub;
- published asset set checked with `sha256sum -c --strict SHA256SUMS`, exactly
  four `.deb` and four `.rpm` dot-named packages, no tilde names, no
  `0.0.1` placeholder, prerelease flag set;
- post-publication fresh-host lane on the rc.2 tag with
  `quick_install_version=0.4.0-rc.2`;
- pinned quick-install dry run resolves the published rc.2 artifacts.

**Exit:** rc.2 published and verified; the rc.1 → rc.2 package upgrade is the
supported successor path for the field upgrade drill.

### Stage C — field qualification

Preconditions, all of which must be true before the host is touched:

- the reference profile (canonical text: [DEPLOYMENT-ARCHITECTURE.md](../DEPLOYMENT-ARCHITECTURE.md)
  §5 UC-11) is approved and merged;
- this plan is merged;
- the field host is provisioned, recorded, and not the shared CI runner;
- the acceptable-limitation and termination lists in §6.9 are agreed.

Then execute §6. No source builds, local patches, or unreleased artifacts may
be used in the field run. If a fix is required mid-campaign, it goes into
rc.3, is published, and the field evidence for the new artifact is labelled
separately; do not edit the running deployment in place.

**Exit:** §7's stable gate is met.

### Stage D — stable `v0.4.0`

- Tag the **exact rc.2 commit** (or the rc.3 commit if field work required
  one) as `v0.4.0`; no product commits between the final RC and the stable
  tag.
- The stable release workflow validates the `[0.4.0]` changelog section,
  builds the same code, publishes as a **non-prerelease**, and must produce
  the same asset/checksum contract as the RC (with stable names).
- Verify `releases/latest` resolves `v0.4.0`, the tarball sidecar verifies,
  the package set matches `SHA256SUMS`, and internal package versions are
  `0.4.0` (no `~rc` suffix).
- Immediately after the tag, publish `docs/release/v0.4.0-release-notes.md`
  and `docs/release/v0.4.0-support-matrix.md` (or update the living
  equivalents) as part of the D4 follow-up, and link them from the editable
  release body.
- Also immediately after the tag, land the **post-stable installer truth** change:
  `fallback_version="0.4.0"`, replace "v0.3.0 latest stable" in
  `DEPLOYMENT.md`, `install/from-github-release.md`, and the README, and run
  the **unpinned** quick installer for the first time.

**Ordering note (must be decided before the tag):** the field report and the
`FIELD-QUALIFIED` markers are docs/evidence changes produced by Stage C. To
honour [release-process.md](../release/release-process.md)'s "no new commits
between the final RC and the stable tag" rule, the recommended ordering is:
tag stable at the exact rc.2 commit, then merge the field report and support
matrix update as an immediate docs-only follow-up, and link them from the
editable GitHub release body. The alternative — a docs-only commit before the
tag — requires an explicit policy exception and disclosure that the binaries
are unchanged. Do not silently pick one; record the choice in the release
record. See §10.

### Stage E — hand off to MH-A

Only after stable and the field decision exist:

1. Start transition-plan P1 (remote dispatch/transport/PKI) per ADR-029.
2. Keep the field profile as the supported baseline; do not claim multi-host
   until P1/P2 pass the L3 gate on separate kernels/hosts.
3. Keep Volvisor deferred until MH-A transport and field evidence exist and
   the Volvisor pin is re-reviewed.

## 5. Reference profile

The canonical profile is recorded in
[DEPLOYMENT-ARCHITECTURE.md](../DEPLOYMENT-ARCHITECTURE.md) §5 UC-11.
In summary:

| Dimension | Profile |
|---|---|
| Topology | **One host** running control plane, agent, stord, nwd, and nginx; internal listeners loopback; nginx is the edge |
| Host | Ubuntu 24.04 noble, amd64; **bare metal preferred**. A KVM-capable cloud VM is allowed only when it exposes `/dev/kvm`, and it is recorded as virtualized — never described as bare metal. Hardware is recorded, not promoted to a minimum |
| VMM | Cloud Hypervisor **v53.0**, digest-verified by the installer |
| Artifacts | Published **`.deb`** set for the tag, installed by the published quick installer pinned to that tag; the upgrade drill starts from the published rc.1 tarball and moves to rc.2 packages. RPM excluded |
| Storage | Local directory + **LVM**; no iSCSI/Ceph/Volvisor |
| Network | Default single-host bridge only; no VLAN, no fabric/VXLAN |
| Lifecycle | Core-managed authority; **stop-first**, not pause-first |
| Workload | 3–5 VMs; repeated create/delete; start/stop/reboot; console; one policy change; LVM attach/use |
| Upgrade | `v0.4.0-rc.1` → `v0.4.0-rc.2` package upgrade on the field host |
| Data | **Disposable qualification data only** — no backup means no data-protection claim |
| Duration | 21 days minimum, 30 preferred |

**Why one host.** The CP→agent dispatch surface is a local Unix-socket path and
the agent has no TCP gRPC listener; remote nodes cannot be enrolled or driven.
The Prompt 06 example of one control plane plus two or three compute nodes is
therefore not a coherent profile for this release. Narrowing the topology is
the honest choice; a multi-node deployment would not exercise a supported
product path.

**What this profile does not claim:** multi-host, HA, control-plane failover,
migration (the M4.6 quiescent two-stord primitive is not a product migration
feature), backup/restore (hard-fenced `501`), scale/density/throughput,
RPM, arm64, hardware minimums, S3/object-storage credentials, or Volvisor.

## 6. Field campaign execution

### 6.1 Pre-flight (before the window starts)

Record and commit to the evidence directory:

- host identity (redacted), CPU model/flags, `/dev/kvm` presence, memory,
  disk layout, kernel, firmware, Cloud Hypervisor build, OS image digest;
- CHV package versions and their checksums; the exact rc.2 tag and release
  asset digests;
- network topology and the edge/TLS configuration (redacted);
- storage layout and the exact volume classes used;
- baseline resource snapshot: daemon RSS/CPU, DB size, open fds/sockets, CHV
  processes, taps/veth/bridges/netns, nftables object counts, stord session
  and volume rows.

Rehearse the upgrade path in the reference topology: install rc.1 from the
published artifacts (tarball/`install.sh`), run a VM, upgrade the packages to
rc.2, restart the services per the documented procedure, verify config, DB,
certificates, the operator account, VM survival, and the node's reported
version. Then uninstall/purge and perform a clean rc.2 install. The clean rc.2
install is the one the field window starts from, so the window proves
reproducibility from published artifacts and docs.

### 6.2 Deployment from released artifacts

Use only the published rc.2 packages/tarball and the documented install path.
No source builds, no local patches, no `cargo run`, no unreleased images. If a
documented step is wrong or missing, that is an operational defect: record it,
fix the doc in a follow-up, and repeat the clean install rather than
improvising silently.

### 6.3 Normal workload

Run a bounded workload long enough to observe steady state:

- 3–5 VMs, repeatedly created and deleted across the window;
- start/stop/reboot cycles, including a VM left running across daemon
  restarts;
- serial console and normal operator visibility (UI, CLI, API);
- one live network-policy change with a before/after connectivity check;
- LVM-backed volume attach/use/detach, including a delete that closes the
  session.

Do not invent a mid-window upgrade: the campaign runs on rc.2, so there is no
successor unless a fix forces rc.3. The rc.1 → rc.2 drill is executed in the
reference topology before the window (and repeated if a successor RC appears).

### 6.4 Planned failure and recovery drills

Each drill records the contract, the observed behavior, the recovery time, and
whether any residue remained. Run each at least once; repeat the destructive
ones only after the deployment is healthy again.

| Drill | What must hold |
|---|---|
| Control-plane restart | CP returns; running VMs unaffected; mutations resume; no duplicate operation effects |
| Control-plane outage (kill, observe, restore) | Published partition policy holds; running VMs continue; queued mutations fail or replay per contract; no split authority |
| Agent restart with running VMs | VMs survive; desired state converges; no detached-open stord sessions (#711) |
| stord restart during/after an operation | Sessions reconcile; failed operations are visible with a safe next action; no silent `Active` |
| nwd restart / network disruption | Policy and bridge re-materialize; no unintended guest connectivity gap; no orphan taps/nft |
| **Real host reboot** with running VMs | Units return; VM state and data are preserved; the documented recovery action brings VMs back (auto-start or an explicit start); no orphan processes/taps/netns/nft |
| Certificate/enrollment failure (safe reproduction) | Fails closed with a clear diagnostic; documented recovery works; first enrollment's `ReportBootstrapResult` is accepted, not rejected by the peer-node-id check (#709) |
| Upgrade rc.1 → rc.2 in the reference topology | Install rc.1, run a VM, upgrade packages to rc.2, restart per the documented procedure: config, DB, certs, operator account, and the VM survive; the node row reports rc.2; the downgrade boundary is stated |
| Delete-after-agent-restart | VM delete closes the volume session; no orphaned `open` row (#711) |
| Failed upgrade / rollback | The documented manual rollback path is followed; no data loss; downgrade remains explicitly unsupported |

### 6.5 Observability and operator usability

For each question, record whether the operator can answer it from supported
tools, and what was missing:

- which VMs are running, and on which node;
- node health, readiness, and **reported version**;
- failed or stuck operations and the reason;
- migration progress — out of profile for this release; record that it is not
  offered as a supported action;
- storage and network failures;
- certificate/enrollment failures;
- resource pressure;
- what action is safe next.

Missing metrics, logs, or runbook steps are operational defects, not
documentation niceties.

### 6.6 Resource and leak checks

Across the campaign, check for unexplained growth or residue in:

- daemon RSS/CPU and restart counts;
- SQLite/DB size and WAL behavior;
- open files/sockets per daemon;
- Cloud Hypervisor processes;
- TAP/veth/bridge/netns objects;
- nftables tables/chains/rules;
- stord volume/session state;
- temporary backup/migration artifacts (none should be created in this
  profile).

### 6.7 Cadence

- **Daily:** daemon/unit health, node health and version, VM states, failed
  operations, `/metrics` endpoints, disk/inode growth, orphan scan.
- **Weekly:** create/delete batch, lifecycle cycle, console check, policy
  change, LVM attach/detach, log review for errors that did not page.
- **Drill days:** schedule destructive drills early in the week so there is
  time to recover and observe steady state before the weekend.
- **End of window:** final leak scan, final upgrade/rollback check, and the
  support decision.

To be produced under

| File | Contents |

Do not create filled reports before the run. The directory and the decision
document are deliverables of Stage C, not placeholders.

### 6.9 Pass/fail classification

**Terminate the field qualification and fix before stable (blocker-class):**

- guest-to-host or guest-to-guest isolation breach;
- data corruption or loss on the qualified storage path;
- authority split or state divergence that does not self-heal;
- failure to recover after a documented restart/reboot;
- credential or key exposure;
- VM/process/volume/network residue that survives documented cleanup;
- upgrade destroys configuration, database, certificates, or the operator
  account;
- an unresolved defect that requires hidden maintainer knowledge for ordinary
  recovery.

**Acceptable only if documented with an operator workaround:**

- missing non-critical metrics or cosmetic UI defects;
- single-host SPOF (inherent and disclosed);
- no backup/HA/migration/multi-host;
- RPM untested;
- pause-first convergence skew (#582) if the profile stays stop-first;
- JWT/encryption-key coupling (#336) if the profile uses an explicit
  `CHV_ENCRYPTION_KEY` and no S3 target;
- audit crash window (#706) and dedicated stord user (#700) as disclosed
  security/operability residuals.

Any "acceptable" item that threatens isolation, data integrity, authority, or
recovery is reclassified as blocker-class. Do not turn an unresolved
blocker-class defect into a documentation-only workaround.

### 6.10 Termination and rollback

If a blocker-class defect appears:

1. Stop new mutations; preserve logs, DB, and evidence.
2. Classify whether running workloads are safe; if not, stop them in the
   documented order.
3. Fix on a branch, cut `v0.4.0-rc.3`, publish it, and restart the field
   window for the new artifact. Field evidence from rc.2 remains labelled
   rc.2; it is not transferred to rc.3.
4. Do not patch the field host in place and continue as if the published
   artifact were tested.

Downgrade is unsupported. Rollback follows the documented manual procedure
and must be rehearsed once, with data-loss boundaries recorded.

## 7. Stable promotion gate

All of the following must be true:

- Stage C exit criteria are met; the field report is filled and approved,
  with **zero blocker-class** defects (merged immediately after the tag under
  the D4 ordering and linked from the release body);
- the stable candidate is the exact rc.2 (or rc.3) commit, with no product
  changes after the final RC;
- the `[0.4.0]` changelog section exists at the tag commit and the release
  workflow's changelog validation passes without `skip_changelog_check`;
- full CI is green on the commit, and a signed annotated tag verifies both
  locally and on GitHub;
- the stable release publishes the expected asset/checksum set, the tarball
  sidecar and `SHA256SUMS` verify, and no RC/tilde/placeholder names leak
  through;
- the support matrix (published under D4) is narrower than or equal to the
  evidence, and every `QUALIFIED`/`FIELD-QUALIFIED` row has a pointer to a
  filled report;
- the release body content is prepared to link the field report and state the
  profile's exclusions (multi-host, HA, backup, migration, scale, RPM, arm64,
  Volvisor); the link is added immediately after the D4 follow-up;
- #666/#556 stay closed only if their lane is green for the stable artifact
  lineage; if the stable tag reuses the rc.2 commit, say so explicitly rather
  than implying a new run;
- #709/#711 are closed only on exact-lineage real-KVM evidence, not on
  adjacent green legs;
- the post-stable installer truth change is prepared before the tag and
  tested immediately after publication.

If any item is missing, **do not publish stable**. Publish rc.3 or hold.

## 9. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| No durable KVM host | Blocks Stage C | Decide host source now; bare metal or KVM-capable cloud VM; never the shared CI runner |
| Field bug forces rc.3 | Slips stable 2–4 weeks | Keep rc.2 scope tiny; classify blockers before the window; only cut rc.3 for blockers |
| No backup in profile | Data loss if misused | Disposable data only; state "not a data-protection solution" in the profile and release notes |
| Single host is a SPOF | Full outage | Disclose; no HA claim; HA remains out of scope until multi-host |
| Version-label bug ships | Misleading upgrade truth | Fix in rc.2; assert the node version after upgrade in the field drill |
| Kernel/VMM variance | New failures | Pin noble + CHV v53.0; record kernel/firmware; treat deviation as out-of-profile |
| RPM adopted untested | Install failure | Deb-only claim; keep RPM labeled built/unexercised |
| #336/#700/#706 residuals | Security/operability debt | Explicit key, no S3, no shared multi-tenant host; disposition in §6.9/§8 |
| Signing keys unavailable | Stable unverifiable | Confirm the signing path before Stage D; do not publish unsigned stable silently |
| Tag-protection bypass remains | Governance risk | Remove/re-justify after the RC window |
| Bus factor (#665) | Campaign stalls | Write the field runbook so a second operator can execute it; keep org-admin items visible |
